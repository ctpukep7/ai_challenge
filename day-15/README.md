# День 15 — управляемые переходы через агента

Учебный стенд на FastAPI, Vue и SQLite показывает, как пользователь ведёт бытовой процесс обычными фразами, а система автоматически превращает разговор в контролируемые действия. Пользователю не нужно знать названия tools, фаз или полей: модель выбирает одно разрешённое действие либо явно решает только ответить. Backend повторно проверяет выбор и не позволяет модели напрямую записать `phase`, `revision`, approval или обойти guards.

## Граница между днями

- **Day 13 — состояние:** этап, checkpoint, pause и точное продолжение.
- **Day 14 — допустимость решения:** проверка structured proposal по инвариантам до вызова модели.
- **Day 15 — право на переход:** evidence, человеческие approvals, guards, revision и безопасный audit попыток.

Наследованный invariant backend Day 14 остаётся совместимым с запросами, содержащими `candidate`, но в основном UI его редактора нет. Day 15 сфокусирован на lifecycle.

## Agent-driven contract

`POST /api/ask` получает UUID `request_id`. Первый вызов модели обязан вернуть ровно одно структурированное решение:

- `define_task` — определить или уточнить задачу в planning, сохранить черновик либо готовый план;
- `save_current_evidence` — сохранить только фактический результат execution;
- `record_validation_result` — типизированно зафиксировать результат проверки: есть ли блокирующие проблемы и их описание;
- `accept_current_evidence_and_advance` — предложить принять актуальный результат и перейти дальше;
- `request_transition` — запросить переход, цель которого выводит сервер;
- `pause_task` и `resume_task` — поставить задачу на паузу или продолжить её.
- `respond_without_action` — ответить без изменения состояния.

Для DeepSeek используется обязательный structured decision, поэтому модель не может молча пропустить выбор действия. Decision context содержит безопасный статус актуального pending и доступность соседних переходов: при открытом pending модель выбирает composite action, а после ручного подтверждения — обычный `request_transition`. Backend проверяет allowlist аргументов, активную сессию, phase и revision. Если в бытовой реплике прямо назван этап — «к выполнению», «к проверке», «закончить/выезжать» — backend **до вызова модели** сам создаёт попытку перехода. Поэтому модель не может заменить просьбу закончить сохранением другого результата. Несоседняя цель не заменяется ближайшей: создаётся rejected attempt с `invalid_target`, где видны запрошенный этап и неизменившийся фактический этап. Ручной диагностический API остаётся отдельным явным действием оператора. Валидный `request_transition` проходит через authoritative state machine и guards. Отклонённое намерение записывается только как safe agent action; guard rejection дополнительно создаёт rejected transition attempt, но успешного event нет.

После серверного решения выполняется второй вызов модели уже **без tools**. Он получает безопасный результат действия и свежий snapshot, а затем объясняет произошедшее естественным языком. Если `define_task` вернул поля длиннее лимитов, до записи в SQLite делается ровно одна внутренняя попытка компактно оформить тот же план; при повторной ошибке приложение показывает бытовой безопасный отказ, не предлагая пользователю сокращать свою задачу. Если второй explanatory вызов недоступен, приложение показывает детерминированное бытовое объяснение и не повторяет уже сохранённое действие.

Один `request_id` исполняется не более одного раза. Повтор HTTP-запроса получает закэшированный результат без повторной мутации.
Frontend сохраняет UUID неуспешной отправки и повторно использует его, пока текст не изменён. Если lifecycle-action уже успел сохраниться до сетевого сбоя, backend восстанавливает ответ из safe action audit; если сбой произошёл раньше action, тот же turn можно безопасно повторить в исходной сессии.

## Evidence и явное человеческое согласие

Planning теперь имеет отдельный серверный признак `planning_ready`. Черновик с действительно блокирующими вопросами сохраняется с `planning_ready=false` и не создаёт карточку подтверждения. Агент задаёт одним сообщением не более 2–3 критичных вопросов. Необязательные сведения он оформляет как явные допущения или диапазоны, а не превращает в допрос. Когда критичных вопросов нет, `define_task` сохраняет готовый план с пустым `open_questions`, выставляет `planning_ready=true` и только тогда создаёт pending подтверждения.

Связь проверяется в обе стороны: `planning_ready=false` требует непустого списка действительно блокирующих вопросов, а `planning_ready=true` требует пустого `open_questions`. Любое изменение общей ревизии задачи инвалидирует pending во всех профильных сессиях. При ручном подтверждении backend ещё раз проверяет revision, готовность плана и отсутствие открытых вопросов.

Generic `save_current_evidence` в planning отклоняется без изменения задачи: иначе модель могла бы заменить draft и получить pending в обход typed `planning_ready`. Создание и любое уточнение плана выполняются только через `define_task`.

Исходная реплика сценария про поездку уже содержит достаточно данных для учебного плана: состав, длительность, автомобиль, бюджет, питание и риск дождя. Точные даты, регион, расход топлива и тип горелки не блокируют план — агент использует разумный резерв. Guard перехода к выполнению требует одновременно непустой план, `planning_ready=true` и человеческое подтверждение.

После перехода checkpoint задаёт сервер по целевой фазе. Поэтому модель не может перенести «уточнить вводные» в execution: там выполняют утверждённый план, а в validation проверяют фактический результат. Ручная диагностика по-прежнему остаётся fallback, однако backend не позволяет вручную подтвердить неготовый план.

После успешного `save_current_evidence` сервер сохраняет данные, но не подтверждает их. Для подходящего evidence создаётся `pending_agent_approval`, привязанный к активной сессии, фазе и ревизии.

Основной путь — явная фраза пользователя, которая одновременно принимает текущий результат и просит продолжить: например, «План мне нравится, давай выполнять дальше». Сервер самостоятельно проверяет текст, находит ровно один актуальный pending той же session/phase/revision и в одной SQLite-транзакции подтверждает его вместе с соседним guarded transition.

Отрицание, вопрос, условность, цитата или расплывчатое «ок» согласиями не считаются. Модель не передаёт approval, target, revision, session ID или approval ID — эти значения выводит backend.

Жёлтая карточка с кнопками остаётся ручным безопасным вариантом:

- **«Подтвердить»** — человеческое решение выставляет соответствующий флаг;
- **«Отклонить»** — закрывает pending без изменения approval.

После ручного **«Подтвердить»** пользователь может написать «Подтверждаю план, переходим к реализации»: открытого pending уже нет, но сохранённый approval и guards разрешают обычный соседний переход. Если модель ошибочно повторно выберет composite action, backend применит тот же fail-safe контракт — только для уже подтверждённого результата, явной просьбы продолжить и пройденных guards. Выполняется ровно одна попытка и одно событие перехода.

Если phase или revision уже изменились, confirmation истекает и не может изменить задачу. Таким образом, агент не подтверждает собственный результат. Артефакт `plan_artifact` в интерфейсе называется **«План подготовки»**: он может включать не только перечень вещей, но и действия, ограничения и договорённости.

## Типизированный результат проверки

На этапе validation generic `save_current_evidence` запрещён: положительное резюме вроде «блокирующих замечаний нет» нельзя случайно сохранить как непустой blocker. Агент обязан выбрать `record_validation_result`:

- `has_blockers=true` и непустой `blocking_issues` сохраняют проблемы, сбрасывают `validation_passed` и не создают pending; в интерфейсе это жёлтое предупреждение «Найдена блокирующая проблема», а не зелёный успех;
- `has_blockers=false` требует пустой `blocking_issues`, очищает прежние проблемы, сбрасывает `validation_passed` и создаёт ровно один pending финальной проверки;
- противоречивые пары аргументов отклоняются без изменения задачи;
- полный текст проблемы остаётся в task state, но не попадает в safe agent-action audit.

Повторная чистая проверка заменяет предыдущий pending: старый становится expired, актуальным остаётся один. В ручной диагностике очистка поля не обещает карточку: после сохранения становится доступна отдельная кнопка **«Проблем нет — подтвердить проверку вручную»**. Она использует user API и не создаёт вымышленное действие агента.

## Сценарий «Поездка с друзьями»

Слева находятся phase-aware пресеты. Они **только заполняют composer** и ничего не отправляют автоматически. Пользователь видит и отправляет каждое сообщение самостоятельно.

- первая реплика автоматически превращается в задачу и предложенный план;
- попытка сразу начать сборы создаёт реальную отклонённую попытку перехода;
- попытка из планирования сразу попасть к проверке остаётся отдельной отклонённой попыткой `invalid_target`, а не превращается в выполнение;
- явное согласие с планом атомарно подтверждает его и начинает подготовку;
- рассказ о собранных вещах становится результатом выполнения;
- пауза и продолжение сохраняют текущий шаг и результаты;
- забытый паспорт блокирует завершение, пока пользователь не сообщит, что проблема устранена;
- финальная явная фраза подтверждает проверку и завершает процесс.

Каждый ответ с действием содержит детерминированную карточку: принято или отклонено, action, reason code, phase и revision до/после. Текст модели остаётся пояснением, а доказательством работы механизма служит серверная карточка и audit справа.

## Интерфейс

- слева — сценарные сообщения для текущей фазы;
- по центру — основной чат и pending approvals;
- справа — authoritative evidence, guards, transition audit, agent-action audit и checkpoint;
- прямые формы изменения состояния скрыты внутри закрытого блока **«Ручная диагностика»**.

Правую панель можно менять по ширине за левую границу. Значение хранится в `localStorage`; разделитель поддерживает `←`, `→`, `Home` и `End`. До 900 px интерфейс складывается вертикально: сценарий, чат, state panel.

Composer увеличен для длинных бытовых сообщений и остаётся доступным во время pause: агент может объяснить состояние или запросить `resume_task`. После `done` чат также доступен для read-only объяснения, но сервер не разрешит новые lifecycle-мутации. Ответ без изменения процесса помечается нейтральной карточкой и не создаёт запись действия в audit.

## Guard matrix

| Переход | Проверяемые prerequisites |
| --- | --- |
| `planning → execution` | непустой `plan_artifact`, `planning_ready=true` и человеческий `plan_approved=true` |
| `execution → validation` | непустой `execution_result` и `implementation_ready=true` |
| `validation → done` | `validation_passed=true` и пустые `blocking_issues` |

Автомат однонаправленный: обратных переходов нет. При невыполненном условии задача остаётся на текущем этапе, а агент объясняет, что нужно завершить.

## Беззвучный сценарий видео

Записывайте весь экран без голоса. После каждого ответа задерживайтесь на 3–5 секунд и переводите внимание курсором между чатом, состоянием и журналами справа. Каждая кнопка слева только заполняет поле: перед отправкой зритель должен увидеть бытовую реплику.

1. Выполните полный reset. Покажите профиль «Обычный», пустой чат, этап «Планирование», rev 0 и пустые журналы.
2. Нажмите **«1. Рассказать о поездке»**. Покажите заполненный длинный текст и отправьте его.
3. После ответа покажите предложенный план, статус **«план готов к подтверждению»**, жёлтую карточку ожидающего решения и зелёную карточку «Задача и предложенный план». Обратите внимание: агент не спрашивал даты, регион, расход топлива или тип горелки — необязательные детали стали допущениями. Ничего вручную в технических формах не вводите.
4. Нажмите **«2. Попробовать без плана»** и отправьте. Покажите красную карточку отказа, неизменившийся этап и rejected attempt справа.
5. Нажмите **«Попробовать перейти к проверке»** и отправьте. В журнале покажите `invalid_target`: «запрошен этап: Проверка», «фактический этап не изменён: Планирование».
6. Нажмите **«3. Принять план и продолжить»**. На секунду задержитесь на фразе «План мне нравится, давай выполнять дальше», затем отправьте.
7. Покажите, что одним сообщением решение стало подтверждённым и этап сменился на «Выполнение». Checkpoint справа должен говорить о выполнении утверждённого плана, а не об уточнении вводных. В audit должна появиться карточка **«Ваше согласие и переход дальше»**.
8. Нажмите **«Сделать паузу»**, отправьте и покажите статус паузы. Затем нажмите **«Продолжить подготовку»** и покажите, что план и текущий шаг не потерялись.
9. Нажмите **«Рассказать, что уже собрано»**, отправьте. Покажите полный результат: еда, вода, снаряжение, документы, топливо и распределение обязанностей — и новое ожидающее решение.
10. Нажмите **«Принять результат и проверить»**, отправьте. Покажите переход к «Проверке» без нажатия ручной кнопки подтверждения.
11. Нажмите **«Сообщить о забытом паспорте»**, отправьте. Покажите блокирующее замечание справа.
12. Нажмите **«Попробовать закончить сейчас»**, отправьте. Покажите отказ guards и две причины: проверка не подтверждена и осталась проблема.
13. Нажмите **«Сообщить, что всё исправлено»**, отправьте. Покажите typed action «Результат финальной проверки», пустой список проблем и ожидающее решение.
14. Нажмите **«Подтвердить и завершить»**, отправьте. Покажите этап «Готово», accepted attempt/event и финальную ревизию.
15. Нажмите **«Подвести итог»**, отправьте. Покажите нейтральную карточку «Ответ без изменения состояния» и неизменившуюся ревизию.

Главное визуальное доказательство: пользователь всё время говорит бытовыми фразами; модель структурирует намерение, но окончательное решение принимает сервер. Даже явное согласие проходит через актуальный pending и guards, а запрещённая попытка остаётся в audit.

## Что проверить после прогона

### Логи

- каждый agent-turn отправляет валидный UUID `request_id`;
- новый изменяющий turn обычно вызывает provider дважды: structured decision, затем естественное объяснение без tools;
- `respond_without_action` — явный структурированный выбор для обычного ответа, но не lifecycle-мутация;
- accepted и rejected actions возвращают `200`, а результат виден в deterministic card;
- при использовании ручного fallback confirm/reject обращаются к `/api/agent/approvals/{id}/...`;
- pause допускает следующий чат-запрос на resume;
- done допускает read-only ответ.

### SQLite

- `agent_turns`: request ID завершён один раз;
- `agent_actions`: максимум одно действие на turn, только safe metadata; полный blocker text не сохраняется;
- `pending_agent_approvals`: pending → confirmed/rejected/expired;
- `tasks`: evidence может быть сохранён при false approval;
- `task_transition_attempts`: rejected и accepted попытки с reason codes;
- `task_transition_events`: только успешные переходы;
- audit не содержит prompt, полного evidence, profile data или provider payload;
- `PRAGMA integrity_check` возвращает `ok`.

Полный reset также очищает agent turns/actions/approvals и обнуляет разрешённые AUTOINCREMENT sequences. Четыре встроенных профиля восстанавливаются, «Обычный» становится активным.

## API

- `GET /api/state` — authoritative state, evidence, guards и audit;
- `POST /api/ask` — agent turn с `request_id`;
- `POST /api/agent/approvals/{id}/confirm` — подтвердить pending approval;
- `POST /api/agent/approvals/{id}/reject` — отклонить pending approval;
- `PUT /api/task/evidence`, `POST /api/task/evidence/decision`, `POST /api/task/transition` — ручной диагностический путь.
