# День 17 — агент с MCP-инструментом календаря

Это самостоятельная копия приложения Дня 12: чат, профили и память сохранены, но к агенту добавлен локальный MCP-сервер. Профили находятся в «Настройках» → «Профили», а слева остаются только диалоги. Код Дня 12 не меняется.

## Что здесь делает агент

1. Приложение запускает `mcp_server.py` как локальный процесс и устанавливает MCP-соединение через `stdio`.
2. MCP-клиент запрашивает описание инструментов `list_upcoming_events`, `list_calendars` и `create_event`. Модели доступны схемы чтения событий, предложения нового события и локального уточнения `clarify_event` (это не MCP-инструмент); список календарей приложение получает само при подготовке предложения.
3. Для вопроса о расписании модель может запросить `list_upcoming_events`, например с `days: 7`. Приложение проверяет аргументы, вызывает MCP-инструмент и передаёт результат модели. При необходимости агент может после чтения подготовить предложение события; число шагов модели ограничено тремя, повторное одинаковое чтение не выполняется.
4. При явной просьбе создать встречу агент не принимает обычный текстовый ответ за результат: модель должна предложить название, начало и конец либо задать конкретный уточняющий вопрос. Уточнение — локальный шаг модели, а не вызов MCP. Для предложения приложение получает доступные календари, сохраняет проект и показывает его пользователю. На этом этапе **в календаре ещё ничего не создано**.
5. Только после проверки полей, выбора календаря и нажатия «Создать событие» приложение вызывает MCP-инструмент `create_event`. Минимальный результат записи возвращается модели; её ответ сообщает о созданном событии. Кнопка «Отмена» не делает запись.

`list_upcoming_events` принимает целое `days` от 1 до 14 (по умолчанию 7) и возвращает время и название не более 50 событий. `list_calendars` возвращает названия и безопасные идентификаторы календарей. `create_event` принимает название, начало, конец, идентификатор календаря и служебный идентификатор операции; последние два поля не выбирает модель. Поддерживается **одно обычное событие со временем**: без участников, повторов, целодневного режима, редактирования и удаления. Карточка «MCP · календарь» показывает шаги по порядку: чтение событий, уточнение без MCP или проект события без записи. Пароль и полный ответ CalDAV она не показывает. Если модель не запросила инструмент для вопроса о расписании, календарь не вызывается; для явной просьбы создать встречу отсутствие проекта или обоснованного уточнения считается ошибкой, а не успехом.

Это отличие от Дня 16: там достаточно подключиться и получить список инструментов; здесь агент действительно вызывает инструмент и использует результат в своём ответе. MCP определяет для этого операции [`tools/list` и `tools/call`](https://modelcontextprotocol.io/specification/2025-11-25/server/tools).

## Подготовка

Нужны Python 3.11+, Node.js 20+, доступ к провайдеру модели (DeepSeek или OpenRouter) и личный Яндекс Календарь. Для календаря создайте **пароль приложения** категории «Календарь» в Яндекс ID. Обычный пароль от аккаунта сюда вводить не нужно. Яндекс описывает настройку CalDAV и адрес `https://caldav.yandex.ru` в [официальной инструкции](https://yandex.ru/support/yandex-360/customers/calendar/web/ru/data-exchange/synchronization/sync-desktop). Новый пароль приложения может начать работать не сразу.

```bash
cd day-17
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
npm ci
npm --prefix frontend ci
cp .env.example .env
```

В локальном `.env` укажите ключ одного из поддерживаемых провайдеров и параметры календаря:

```dotenv
DEEPSEEK_API_KEY=ваш_ключ_модели
# или OPENROUTER_API_KEY=ваш_ключ_модели
YANDEX_CALDAV_USERNAME=ваш_логин_Яндекса
YANDEX_CALDAV_APP_PASSWORD=пароль_приложения_Календарь
```

Не показывайте `.env` в видео и не добавляйте его в Git. Если ключа модели нет, приложение не сможет показать полный цикл «модель → MCP → модель». Без данных Яндекс Календаря локальные тесты и получение списка MCP-инструментов работают, но чтение событий и получение календарей для создания вернут ошибку настройки. Для создания не нужен отдельный ключ Яндекс API: используются те же логин и пароль приложения CalDAV. Живое подключение и запись в ваш аккаунт нельзя считать проверенными до запуска с вашими собственными учётными данными.

## Запуск

```bash
npm run dev
```

- интерфейс: `http://127.0.0.1:5183`
- API: `http://127.0.0.1:5016`

Оба процесса работают, пока открыта команда `npm run dev`. После демонстрации остановите их сочетанием `Ctrl+C` в том же терминале.

Откройте интерфейс, проверьте провайдера модели в «Настройках» → «Модель» и задайте вопрос: «Какие события у меня в календаре на ближайшие 7 дней?». Кнопка примера только заполняет поле ввода — для запроса нажмите «Отправить».

Чтобы создать событие, нажмите пример «Создать встречу», замените заполнители конкретным названием и **будущими** датами/временем с явным смещением часового пояса (формат `YYYY-MM-DDTHH:MM:SS+06:00`) и отправьте запрос. Название должно содержать от 1 до 120 символов; конец — быть позже начала, длительность — не более 24 часов. Проверьте предложение в блоке под перепиской: название, начало, конец и календарь назначения. При одном календаре он выбирается заранее, при нескольких выберите нужный самостоятельно. Пока предложение открыто, отправка другого сообщения недоступна. «Отмена» закрывает предложение без записи; «Создать событие» выполняет запись один раз.

Можно сформулировать запрос естественно: «Создай встречу завтра с 13:00 до 14:00 по омскому времени, название — Демо». Агент получает текущее время для интерпретации «завтра» и знает, что Омск — `Asia/Omsk`; повторно спрашивать пояс при таком запросе он не должен. Для других городов укажите часовой пояс или смещение: пояс сервера не считается вашим. Если интервал противоречит длительности (например, «на два часа с 13:00 до 14:00») или не хватает даты/времени, агент должен уточнить это до предложения. Создание всё равно требует отдельного подтверждения в интерфейсе.

Если после отправки запроса появилась ошибка модели или MCP, этот запрос **не сохранён**. Ответы и карточки выше относятся к предыдущим запросам, а не к текущей ошибке. Диагностика ошибки модели ограничена этапом и HTTP-статусом, когда он доступен; по одному сообщению об ошибке нельзя уверенно установить её первопричину.

Если после подтверждения показано «Исход неизвестен», соединение могло оборваться уже после записи. **Сначала проверьте Яндекс Календарь; не отправляйте то же событие повторно вслепую.** Повторное подтверждение той же операции не должно создавать дубликат. Если календарь записал событие, но второй ответ модели не удался, приложение сохраняет факт записи и показывает резервный ответ.

## Как показать выполнение задания на видео

1. Покажите в `mcp_server.py` регистрацию `list_upcoming_events`, `list_calendars` и `create_event`, их параметры и результаты. Обратите внимание: создание — отдельный инструмент, а не продолжение чтения.
2. Запустите `npm run dev` и откройте чат Дня 17. Секреты в `.env` и настройках провайдера не показывайте.
3. Отправьте вопрос о ближайших событиях. Для наглядности заранее добавьте в личный календарь одно безопасное тестовое событие с нейтральным названием.
4. Под ответом покажите карточку «MCP · календарь»: шаг `list_upcoming_events` с `days: 7`, число событий и использование тестового события в ответе. Если агент сначала прочитал календарь, а затем предложил событие, карточка покажет оба шага по порядку.
5. Для демонстрации создания нажмите «Создать встречу», замените заполнители нейтральным названием и будущим временем по Омску, затем отправьте запрос. Покажите проект и статус «Предложено · без записи»; при нескольких календарях выберите нужный. Сверьте время и покажите, что до подтверждения события нет.
6. Нажмите «Создать событие» **один раз**. Покажите статус «Создано», ответ агента и запись в Яндекс Календаре. Используйте тестовое название без личных данных. Если не хотите записывать событие во время видео, нажмите «Отмена» и честно покажите только защиту от записи; это не подтверждает успешную работу `create_event`.

«Без вызова» при вопросе о расписании означает, что модель не обращалась к календарю; это не доказательство работы MCP. Для явной просьбы создать событие приложение должно показать проект или нужное уточнение, а не выдавать ответ без инструмента за успех. Если видите сообщение об ошибке, не приписывайте ему карточку от предыдущего ответа.

## Данные и Git

В Git входят исходники, тесты, инструкции и lock-файлы зависимостей.
Все значения в `.env.example` пустые. Настоящий `.env` и его варианты,
SQLite с диалогами, профилями, памятью и проектами событий, файлы WAL/SHM,
логи, окружение Python, зависимости и сборка исключены через `.gitignore`.
Демонстрационные видео исключены общими правилами репозитория.

Во время работы контекст диалога и результат чтения календаря передаются
выбранному провайдеру модели. MCP возвращает для событий только название,
начало и конец; описания и участники не передаются из календаря.
Логин и пароль приложения используются локальным MCP-процессом для подключения
к Яндекс CalDAV и не включаются в сообщения модели. Это API-обмен приложения,
отдельный от состава Git-коммита. Для демонстрации используйте нейтральные
названия событий без личных данных.

## Проверка без личного календаря

```bash
source .venv/bin/activate
.venv/bin/python -m pytest backend -q
npm run build
```

Тесты проверяют MCP `tools/list` и вызовы через локальный `stdio`, валидацию аргументов чтения и создания, предложение без записи, последовательность чтение → проект, предел шагов и защиту от повторного чтения, уточнение противоречивого времени, омский часовой пояс, отмену, выбор календаря, защиту от повторного подтверждения и неопределённый исход сетевой записи. Модель и CalDAV-клиент в тестах подменены: доступ к личному календарю и настоящие ключи не требуются. Production build проверяет интерфейс отдельно. Автоматические тесты **не создают** реальное событие; живую проверку выполняйте только вручную и с явным подтверждением в интерфейсе.

Для текущей версии локально прошли 80 backend-тестов и production build. Отдельный живой запрос к модели и MCP сформировал проект события со статусом `proposed` и ожидающим подтверждением; эта проверка не нажимала «Создать событие» и не проверяла запись в календарь.
