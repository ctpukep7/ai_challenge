# Pipeline · День 31 — ассистент разработчика

Ассистент работает с **текущим репозиторием AI Challenge**: README/docs через
RAG, публичные исходники и текущие изменения через настоящий MCP stdio.
DeepSeek сам выбирает инструменты. `/help` показывает обзор,
`/help <вопрос>` и обычный вопрос работают одинаково.

## Структура Day31

Backend находится в `day-31/backend/`: FastAPI API в `app.py`, модельный цикл
в `agent.py`, отдельный DeepSeek function-calling клиент в `provider.py`, MCP
сервер в `mcp_server.py`, политика публичных файлов в `project_tools.py`.
Frontend — `day-31/frontend/src/` (Vue/Vite). Общие RAG-классы переиспользуются
из устанавливаемого `packages/assistant_core`; Day32/33 не используют новый цикл.

## Установка и запуск

Из корня репозитория (Python 3.12, Node.js 22+):

```bash
python3.12 -m venv .assistant-venv
.assistant-venv/bin/pip install -r packages/assistant_core/requirements.lock.txt
.assistant-venv/bin/pip install --no-build-isolation -e packages/assistant_core
npm --prefix day-31/frontend ci
cp day-31/.env.example day-31/.env
```

В локальном `.env` задайте `DEEPSEEK_API_KEY`. Ключ не входит в Git и не
передаётся MCP-процессу. Из `day-31`: `npm run dev` запускает API на
`http://127.0.0.1:5030`, интерфейс на `http://127.0.0.1:5196`.
Production: `npm run build && npm start`; интерфейс доступен на API-порту.
Ctrl+C завершает dev-процессы.

FastEmbed работает только с существующим кэшем
`day-21/.cache/fastembed` или `ASSISTANT_EMBED_CACHE`. При переносе скопируйте
этот кэш; автоматического скачивания нет. Модель multilingual MiniLM-L12-v2,
384 измерения, 126 содержательных токенов. Новые веса LLM не нужны.
Для вопросов по документации сначала нажмите «Построить индекс».
Git и исходники доступны независимо от готовности RAG-индекса.

## Как работает модельный цикл

На запрос запускается один настоящий MCP stdio-процесс: discovery публикует
JSON Schema инструментов, DeepSeek возвращает `assistant.tool_calls`, host
проверяет имя/аргументы и выполняет выбранные вызовы. Исходное assistant
сообщение и tool-ответы с соответствующими `tool_call_id` отправляются модели
до итогового JSON. Подбора инструментов по регулярным выражениям нет.

Каталог:

- `search_documentation(query, day?, scope="all")` — RAG по корневому README,
  `day-NN/README.md`, `docs/**/*.md`; до 5 результатов cosine top12 с порогом
  0.35. При указанном дне — до 3 фрагментов его README и до 2 из docs.
  До 2 соседних фрагментов того же документа восстанавливают границы
  предложений; neighbor имеет `score=null`.
  Для общепроектных вопросов модель выбирает `scope="project"`: только
  корневой README и docs, до 5 релевантных anchors с представленностью обоих
  видов документов, если их сходство не ниже 0.35. Сходство не повышается
  искусственно. `project` несовместим с `day`; default `all` сохраняет поиск
  по всем дням. Выбор инструмента и области делает модель, не regex-роутер.
- `git_branch()` — текущая ветка, SHA и detached HEAD из Git.
- `list_project_files(prefix?)` — до 300 разрешённых публичных путей.
- `read_project_file(path, start_line=1, end_line?)` — до 200 строк / 16 КБ
  публичного UTF-8 исходника, README или конфигурации.
- `git_diff(scope="all", path?)` — `all` относительно HEAD, `working`
  относительно index, `staged` относительно HEAD. Только публичные пути;
  безопасные untracked-файлы помечены `untracked snapshot`.

Корень фиксирован сервером. Записи файлов, shell-команд, commit/push и
произвольного root нет. Разрешены публичные README/docs, исходники
backend/frontend/scripts/tests дней, исходники packages и явно выбранные
конфигурации. `.env` (включая example), wiki, Memory Bank, данные/fixtures,
веса, зависимости, сборки, видео, сырая транскрибация `final week.md`, symlink,
бинарные файлы, файлы свыше 300 КБ и распознанные секреты исключены.
Это ограниченный публичный контекст, а не полный просмотр рабочей папки.

Diff сначала фильтрует **имена**, затем читает содержимое отдельных разрешённых
файлов. Встроенные Git external diff/textconv отключены. До 30 патчей / 32 КБ;
сводка содержит до 300 публичных изменённых путей, общее количество и явную
неполноту. Секретные пути не раскрываются; число пропусков показано.

Лимиты запроса: 6 модельных шагов, 10 запросов инструментов, до 3 за шаг;
15 секунд на инструмент (25 на RAG), 180 секунд всего, до 80 КБ контекста
инструментов. Некорректное имя/JSON/Schema возвращает ошибку модели без вызова
MCP. Достижение лимитов и сбои отображаются явно. Платных повторов после
ошибки провайдера нет; исправление моделью аргументов ограничено тем же циклом.

## Источники и наблюдаемость

Host присваивает ID только фактически полученным фрагментам. Итоговые claims
проверяются по ID и точному вхождению цитаты в текст evidence. Документация,
код, Git и diff имеют разные виды источников. Ветка подтверждается Git,
а не документом. Проверка цитат подтверждает происхождение, но не доказывает
смысловую правильность ответа.

При ошибке отдельного утверждения host один раз возвращает модели безопасные
коды ошибок, известные host evidence ID и небольшой каталог `quote_options`.
Каталог содержит неизменные непрерывные фрагменты реального evidence с
`quote_id` и `source_id`; весь feedback ограничен 2000 UTF-8 байтами. Для
проблемного источника приоритет имеют релевантные строки, для списка файлов —
разные папки (например, backend и frontend). Модель может явно выбрать
`{text, source_id, quote_id}` либо вернуть прежний точный `quote`. Host
материализует только выбранный фрагмент и вновь проверяет точное вхождение:
чужой/неизвестный quote ID, несовпадающий source ID или противоречащий quote
отклоняются. Это не подбор цитаты к утверждению и не fuzzy matching. Утверждения
с разными доказательствами нужно разделять, а не склеивать цитаты из разных строк.
Модель получает ровно один дополнительный
шаг для исправленного итогового JSON, с `tool_choice=none`: новые инструменты
на этом шаге не выполняются. Этот шаг входит в прежние 6 шагов / 180 секунд,
учитывается в LLM usage и не является повтором HTTP-запроса при сбое провайдера.
Если свободного шага нет, дополнительного обращения к модели не будет.
Цитаты остаются точными: пробелы, отступы, Markdown, числа и команды не
нормализуются, источник не угадывается, цитата не заменяется host-кодом.

Если исправленный draft снова содержит ошибки, публикуются только строго
проверенные утверждения **этого последнего draft**, с `partial=true` и явной
пометкой частичного ответа. Если проверенных утверждений нет — `unknown` без
выдуманного ответа. Неподтверждённые утверждения не показываются в UI/trace.
Ошибка провайдера или некорректный итоговый JSON остаются `error`, без retry.
Проверка актуальности RAG действует и после исправления цитирования.

Интерфейс показывает время, фактические LLM/MCP-вызовы, токены, источники
с полным текстом. MCP-вызовы представлены отдельными шагами: название,
аргументы, время, результат и успех/ошибка; отклонённый host-запрос явно
отличается от исполнения. Discovery показывает каталог и не считается вызовом
инструмента. Технический JSON доступен отдельно. Источники сгруппированы по
evidence ID и происхождению; все использованные цитаты сохраняются.
Usage отсутствует — отображается
«нет данных», реальный ноль остаётся нулём. Стоимость не угадывается.
Ошибочный и частичный ответы не добавляются в историю. Полностью проверенный
исправленный ответ может войти в историю; UI отмечает исправление цитирования. Markdown/HTML модели не исполняется.
Последние 4 полные пары хранятся только в RAM вкладки и уточняют вопрос;
доказательства каждый раз получаются заново. «Новая беседа» очищает экран,
поле и историю по действию пользователя, без localStorage; при выполнении
запроса кнопка недоступна.

`/help` без вопроса просит модель дать короткий обзор по свежему RAG. Под ним
отдельно показаны три подсказки интерфейса — это заготовки следующих вопросов,
а не сгенерированные факты и не цитаты. Обычные вопросы и `/help <вопрос>`
используют одинаковый модельный цикл. Компактность ответа задаётся prompt,
не обрезанием уже сгенерированного текста.

Документы меняются — индекс становится устаревшим. Инструмент RAG сообщает
об этом и предлагает явное обновление кнопкой; модель не перестраивает индекс.
Если поиск обнаружил отсутствующий или устаревший индекс, host не публикует
последующий документальный ответ из прямого чтения README как `answered`:
вернёт `unknown` с предложением обновить индекс. Код и текущий Git по-прежнему
можно проверять независимо от документального индекса.

Ошибки DeepSeek различают отсутствие ключа, отказ доступа, баланс/лимиты,
соединение, таймаут и некорректный ответ. Вложенные группы исключений stdio
не маскируют известную ошибку провайдера сообщением о недоступности MCP;
независимая неизвестная ошибка в смешанной группе также отмечается безопасным
сообщением. Неизвестные исключения и HTTP-тела не раскрываются пользователю.
Отмена запроса и завершение процесса не превращаются в обычный ответ.
Первоначальная причина единичного живого сбоя из QA не установлена: исправлен
воспроизведённый дефект диагностики, а не доказанный сбой внешнего провайдера.

## API

- `GET /api/index` — ready/stale/documents/chunks.
- `POST /api/index/build` — атомарное обновление локального индекса.
- `POST /api/help` — `{question, history:[{role,content}]}`, до 4 полных пар.
  Ответ: `status=answered|unknown|error`, `answer`, `sources`, `context`,
  `trace`, `warnings`, `metrics`, `validation`, `suggestions` (только для начального `/help`).
  `partial=true` означает, что неподтверждённые утверждения исключены из выдачи.
  При ошибке есть `error_codes`: безопасные категории причин, в том числе
  несколько категорий для смешанной группы исключений.
- Validation: `repair_attempted`, `repaired`, `omitted_claims`, `issues` с безопасными
  `claim_index`/`code` и `source_id`, только если это известный ID из host ledger.
  В issues нет сырых отклонённых утверждений или цитат.
  При полном исправлении текущие issues пусты; первоначальные коды видны в trace.
- Sources: `id`, `kind=documentation|code|git|diff`, `text`, `sha256`, `quote`,
  путь/строки при наличии, score/роль для RAG. Git SHA находится в контексте
  и тексте evidence; `sha256` фрагмента — хеш его текста, у RAG — документа.
- Metrics: `total_seconds`, `llm_calls`, фактические `tool_calls`,
  `tool_requests` (включая отклонённые), `prompt_tokens`, `completion_tokens`,
  `total_tokens`, `evidence_bytes`, `llm` с временем/usage каждого вызова.
- Trace: настоящий `tools/list`, фактические `tools/call`,
  `tool_request_rejected` при host-отказе без MCP-исполнения; отдельные
  `answer/validation` фиксируют отказ/исправление/частичный итог. Это host-проверка,
  а не MCP-вызов; она не увеличивает `tool_calls`.
- Выполненный запрос с ошибкой возвращает HTTP 200 и `status=error`, сохраняя
  уже полученные trace/metrics. Неверный ввод — 422, занятость — 409,
  недоступность локального индекса при index API — 503.

DeepSeek получает вопрос, историю, каталог и результаты выбранных read-only
инструментов: публичные фрагменты, исходники и diff могут уйти провайдеру.

Тесты проверяют RAG/чанкинг/устаревание, project/day-области на реальных локальных
эмбеддингах, function-call протокол, точные цитаты,
пределы цикла/контекста, метрики и ошибки, path/symlink/private/secret политику,
фильтрацию diff до чтения, настоящий stdio discovery/branch/read/list/diff,
потерю диагностики провайдера внутри реального stdio-контекста, вложенные и
смешанные исключения, отмену, группировку цитат и видимую трассу инструментов.

точный выбор quote ID и регрессию плоского inventory backend/frontend,
исчерпание шагов, ошибку провайдера во время исправления, запрет новых MCP на
repair-шаге, stale guard и строгий отказ для изменённых цитат/чужих источников.
Проверяется настоящий MCP stdio с scripted provider и завершением процесса.
Проверки не вызывают платную модель. Живые оценки запускаются отдельно:

```bash
../.assistant-venv/bin/python evaluation/run.py --run-live --ids overview structure-launch branch rag --output data/live-quality.jsonl
```

13 контрольных сценариев в `evaluation/cases.json`: обзор, структура, запуск,
структура с запуском (включая точный вопрос со скриншота пользователя), RAG, ветка, список изменений, конкретный diff, чтение проверки цитат, продолжение
диалога, посторонний вопрос и отказ чтения `.env`. Ожидания не передаются в
prompt или поиск. `--output` сохраняет полный ответ с источниками и трассой
в новый локальный JSONL-файл; data исключена из Git. Результат runner —
эвристическая проверка; полезность и
смысл цитат нужно оценивать вручную. Команда явно выбирает платные сценарии.
Частичный ответ не считается успешным прохождением обычного сценария.
Демонстрационная последовательность с реальными предыдущими ответами в истории:

```bash
../.assistant-venv/bin/python evaluation/run.py --run-live --ids overview demo-launch branch --conversation --output data/demo-live.jsonl
```

Для демонстрации отправляйте свободные вопросы:

1. `/help Где находятся backend и frontend Day31?` — раскройте README/docs.
2. `Какая текущая git-ветка?` — покажите выбранный `git_branch` и Git evidence.
3. `Какие публичные файлы сейчас изменены?` — покажите diff inventory и охват.
4. `Прочитай packages/assistant_core/src/assistant_core/provider.py. Как validate_answer проверяет цитаты?`
   — покажите реальный код и строки.
5. `Прочитай day-31/.env` — подтвердите отказ без доступа к секретам.

Состав и порядок MCP-вызовов определяет модель; они могут различаться.
Это не полноценный code review и не система продуктовых subagent.

Для видео без озвучки достаточно последовательности: `/help` → раскрыть
источники README/docs → спросить о расположении backend/frontend и запуске
Day31 → спросить текущую ветку → раскрыть компактный шаг `git_branch` и его
результат. Оставляйте ответ на экране на несколько секунд для чтения.
«Новая беседа» позволяет начать запись с чистого диалога. Видео записывает
пользователь; в репозитории остаются код и этот сценарий.
