# День 13 — состояние задачи (Task State Machine)

Самостоятельный учебный стенд с FastAPI, Vue и SQLite. Агент хранит формальное состояние задачи: этап, текущий шаг и ожидаемое действие. Профили, сессии и три слоя памяти из Day 12 сохранены.

## Конечный автомат

```text
planning --advance--> execution --advance--> validation --approve--> done
                                      |
                                      +--request_changes--> execution

active planning/execution/validation --pause--> paused --resume--> тот же этап
```

`done` — терминальное состояние. Прямое редактирование `phase` и `run_status` через `PUT /api/task` невозможно. На паузе и после завершения запрещено редактировать весь snapshot задачи. Недопустимый переход отвечает `409 Conflict` и не изменяет ни задачу, ни историю.

При переходе на другой этап API принимает checkpoint назначения — `next_current_step` и `next_expected_action`. Этап, checkpoint, `revision` и событие истории обновляются одной SQLite-транзакцией, поэтому новый этап не может остаться со старым текущим шагом. Пауза и продолжение сохраняют checkpoint без изменений, но также увеличивают `revision`.

Пауза здесь не означает, что приложение должно само считать время бездействия.
Активная задача тоже может сколько угодно ждать пользователя, но при этом API
по-прежнему разрешает новые сообщения, редактирование checkpoint и переходы.
`pause` — явная блокировка: backend запрещает продолжать или менять задачу до
`resume`, а сохранённый статус однозначно показывает, что работа намеренно
приостановлена, в том числе после перезапуска процесса.

При каждом запросе модель получает отдельный структурированный блок `TASK_STATE_MACHINE` с точным snapshot и его `revision`. Он требует продолжать с сохранённого checkpoint без повторного вступления. Во время паузы и после завершения запросы к модели заблокированы до вызова провайдера и до записи сообщений. Если задача изменилась, пока провайдер готовил ответ, результат отбрасывается с `409 Conflict`: ни вопрос, ни ответ в чат не записываются.

## Роли интерфейса и модели в Дне 13

В Дне 13 пользователь сохраняет задачу и выбирает переход через интерфейс.
Модель получает authoritative `TASK_STATE_MACHINE` и отвечает по текущему
шагу; её фраза «задача завершена» не выполняет `approve`. Решение о допустимом
событии принимает pure-автомат `task_machine.py`, а SQLite сохраняет результат.
Таким образом, вопрос и ответ модели отделены от изменения жизненного цикла.

Рабочая задача Дня 13 одна и общая для профилей. `current_step` — сохранённый
шаг внутри этапа, `expected_action` — следующее ожидаемое действие. Это
checkpoint, а не пересказ всей истории чата. На свежей базе задача имеет
`phase=planning`, `run_status=active`, `revision=0`. Смена профиля или новая
сессия меняют разговор, но не создают отдельную задачу и не сбрасывают этап.

После `validation → execution` в Дне 13 появляется возможность доработки:
повторный переход `execution → validation` возвращает задачу к проверке.
Переход к `done` допускается только из validation событием `approve`.
Условия готовности плана или результата ещё не представлены отдельными
машиночитаемыми guards: этот день контролирует граф переходов и checkpoint.

## Сохранение, ревизии и настройки Дня 13

День 13 хранит задачу, профили, сообщения и события успешных переходов в
`data/memory.sqlite3`. `revision` увеличивается при изменении задачи и
переходах, включая pause/resume. Агент фиксирует snapshot перед LLM-вызовом;
при сохранении ответа проверяется, что задача осталась той же ревизии.
Устаревший ответ получает `409 stale_task_state`, даже если внешний провайдер
уже успел его сгенерировать. Такая защита не отменяет выполненный внешний
запрос, но предотвращает запись ответа к уже изменённой задаче.

Стартовые настройки Дня 13: DeepSeek `deepseek-flash`, температура 0,
thinking disabled, полная история сессии. Пустой `max_tokens` означает
отсутствие явного лимита в запросе; заполненное поле допускает 1–4096.
OpenRouter также поддержан. Для Sliding Window/Sticky Facts начальное
окно — 6 сообщений; для Rolling Summary пакет — 10 и остаток — 6.
Таймаут LLM-клиента — 45 секунд, автоматических повторов нет.

Pause в Дне 13 блокирует основной LLM-запрос до вызова провайдера.
После done новый цикл начинается полным сбросом, который очищает также
память и разговоры; это отдельное действие пользователя, а не новый вопрос.
Запросы активной задачи передают вопрос, профиль, память и task snapshot
выбранному внешнему провайдеру. Сохранённая ревизия подтверждает состояние
приложения, а не правильность рассуждений модели.

## Запуск

Требуются Python 3.11+ и Node.js 20+.

```bash
cd day-13
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
npm install
npm --prefix frontend install
cp .env.example .env
npm run dev
```

- интерфейс: `http://localhost:5179`
- API: `http://localhost:5012`

## API

- `GET /api/state` — весь безопасный state, `allowed_events` и последние переходы;
- `PUT /api/task` — цель, ограничения, данные, вопросы, `current_step` и `expected_action`;
- `POST /api/task/transition` — одно из событий `advance`, `approve`, `request_changes`, `pause`, `resume`; переход между этапами требует checkpoint назначения;
- `POST /api/ask` — запрос агенту только в активном нетерминальном состоянии;
- API профилей, сессий, долговременной памяти и полного сброса совпадает с Day 12.

## Демонстрационный сценарий

В интерфейс встроен бытовой сценарий **«Подготовить домашний ужин для друзей»**.
Он позволяет пройти весь автомат без технических знаний: выбрать меню и покупки,
обсудить готовку, проверить результат, вернуть задачу на доработку и завершить её.

1. Нажмите «Заполнить демо-задачу». Кнопка заполнит цель, ограничения, данные, вопросы и checkpoint, но не сохранит их и не изменит этап.
2. Проверьте поля и нажмите «Сохранить задачу».
3. На этапе «Планирование» используйте «Составить меню и план»: кнопка только подставляет запрос в поле, поэтому его можно изменить перед отправкой.
4. Нажмите «Подготовить: Следующий этап». Кнопка только заполнит checkpoint этапа выполнения. Проверьте его и отдельно нажмите «Выполнить: Следующий этап» — этап и checkpoint сохранятся атомарно.
5. Именно на этапе «Выполнение» нажмите «Поставить на паузу». Это не таймер ожидания, а явная заморозка: композер и редактор задачи отключатся, а единственной основной кнопкой станет «Продолжить».
6. Возобновите задачу и сразу нажмите «Продолжай с текущего шага», затем отдельно отправьте подставленный запрос. Откройте «Контекст ответа» и покажите в `task_state_snapshot`, что прежние `current_step` и `expected_action` сохранились, а `revision` увеличилась.
7. Переведите задачу в «Проверку» и попросите проверить блюда, ограничения гостей и готовность к 19:00. Выберите «Вернуть на доработку»: автомат выполнит `validation → execution`. Закройте замечания, снова выполните `execution → validation` и только затем отдельно подтвердите `approve`, чтобы получить `done`.
8. После `done` чат и задача доступны только для чтения; финальное завершение показывает UI, а не формулировка модели на более раннем этапе.

Профили ответа, диалоги, долговременная память и настройки модели собраны в окне «Память и профиль», чтобы не отвлекать от автомата. На новой базе и после полного сброса доступны четыре готовых профиля — «Новичок», «Обычный», «Эксперт» и «Руководитель»; по умолчанию активен универсальный профиль «Обычный». У каждого профиля есть собственный «Диалог 1», а пользовательские профили по-прежнему создаются вручную. Рабочая задача и checkpoint всегда остаются на главном экране.
