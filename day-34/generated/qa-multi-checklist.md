# Чеклист оператора: диагностика ошибок входа (кратко)

Источники: `day-34/generated/qa-multi-checklist.md` (прежняя расширенная версия), `day-33/backend/app.py` (поведение API и коды ошибок).

## Четыре шага диагностики по наблюдениям тикета

1. **Собрать безопасные наблюдения.** Номер дня, действие, точный текст ошибки, шаг воспроизведения, адрес сервиса без токена. Токены, пароли и приватные ключи не запрашивать и не пересылать.
2. **Разделить этапы по коду ошибки.** `HTTP401` — нет подходящего токена (взять действующий у владельца сервиса, не путать с API-ключом DeepSeek); `ERR_CERT_AUTHORITY_INVALID` — браузер не доверяет локальному самоподписанному сертификату, до запроса авторизации дело не доходит; `ERR_CONNECTION_REFUSED` — сервер не запущен или указан неверный адрес/порт (для другого устройства нужен LAN-адрес Mac, а не `127.0.0.1`).
3. **Проверить состояние ассистента Day33.** Ответ `status: unknown` с `reason: missing_ticket_details` — это просьба уточнить данные, а не диагноз; 409 `Сначала постройте индекс` / `Документы изменились` — пересобрать индекс; 409 `Запрос уже выполняется` — дождаться; 404 `Неизвестный тикет` — проверить выбор тикета; 502/503 — сбой провайдера, MCP или кэша модели.
4. **Зафиксировать вывод.** Наблюдения тикета — сведения, а не установленная причина; если подтверждений нет, указать, что причина не установлена, и передать тикет на эскалацию. Проверка TLS не отключается, порт Ollama в интернет не открывается.
