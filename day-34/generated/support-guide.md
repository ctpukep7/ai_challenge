# Памятка поддержки Day33: разбор проблем входа в Day30 по данным обращения

Документ описывает, как оператор поддержки Day33 разбирает обращения о входе в
Day30 (авторизация по токену, HTTPS-сертификат, доступность сервиса), опираясь
только на данные выбранного тикета и на справку продукта. Источники — код и
тесты Day33 (`day-33/backend/app.py`, `day-33/backend/grounded.py`,
`day-33/backend/mcp_server.py`, `day-33/fixtures/support.json`,
`day-33/frontend/src/session.js`, `day-33/tests/test_support.py`,
`day-33/tests/test_grounded.py`) и README Day30 (`day-30/README.md`,
`day-30/backend/app.py`, `day-30/frontend/src/chat-state.js`).

## 1. Что считается «данными обращения»

- Тикеты и пользователи — вымышленные записи в `day-33/fixtures/support.json`.
  У каждого тикета есть `id`, `user_id`, `title`, `status`, `facts`; у
  `INFO-104` дополнительно `needs_details: true`.
- Ассистент получает данные только через read-only MCP-инструменты
  (`day-33/backend/mcp_server.py`): `list_tickets()`, `get_ticket(ticket_id)`,
  `get_ticket_user(ticket_id)`. Произвольного запроса пользователя по `user_id`
  нет — пользователь разрешается только через связь с выбранным тикетом.
- Backend на каждом вопросе заново вызывает MCP и проверяет связь:
  `ticket.id == ticket_id` и `user.id == ticket.user_id`, иначе
  `RuntimeError('Invalid MCP relationship')` → HTTP 503
  (`day-33/backend/app.py`, функция `selected`).
- Наблюдения тикета (`facts`) показываются в интерфейсе отдельным блоком
  «Наблюдения выбранного тикета · MCP» с пометкой «Это сведения тикета, а не
  установленный диагноз» (`day-33/frontend/src/main.js`).

Правило: факты тикета — это наблюдения, а не диагноз. Причина, не подтверждённая
данными, остаётся предположением.

## 2. Порядок разбора обращения

1. Выбрать тикет в селекторе «Учебный тикет». Переключение тикета очищает
   беседу и историю (`select()` в `day-33/frontend/src/session.js`).
2. Убедиться, что индекс справки актуален: статус `ready` и не `stale`.
   Иначе кнопка отправки заблокирована, а API вернёт 409
   («Сначала постройте индекс» / «Документы изменились: обновите индекс»).
3. Задать вопрос по существу, например «Почему не работает авторизация?».
4. Прочитать ответ и проверить три блока: сам ответ, «Справка продукта»
   (источники с путём, строками и точной цитатой) и «Реальные MCP-вызовы
   выбранного тикета» (трасса `list_tickets`, `get_ticket`, `get_ticket_user`).
5. Если статус ответа `unknown` — не выдумывать причину, а запросить у
   пользователя безопасные уточнения.

## 3. Разбор по типам обращений (эталонные тикеты)

### AUTH-101 — HTTP401 после ввода токена
Наблюдения: страница входа открывается, после отправки запроса браузер получает
HTTP401, пользователь ввёл устаревший токен Day30 (значение токена не сохранено).
Что делать: объяснить, что API Day30 требует действующий токен
(`Authorization: Bearer <токен>`), токен создаётся локально в `data/access-token`
и не заменяется при повторной настройке; получить действующий токен у владельца
сервиса, не пересылая его в поддержку. По коду Day30: неверный или отсутствующий
токен даёт 401 `unauthorized`, а частые неудачные попытки входа — 429 с
`Retry-After` (`day-30/backend/app.py`, middleware `security`). В интерфейсе
Day30 401 отображается как «Доступ не подтверждён. Войдите снова с токеном
сервиса.» (`day-30/frontend/src/chat-state.js`).

### TLS-102 — браузер не доверяет сертификату
Наблюдения: `ERR_CERT_AUTHORITY_INVALID` на новом устройстве, Day30 использует
самоподписанный сертификат, до ввода токена дело не доходит.
Что делать: это проблема доверия TLS, а не авторизации. Проверить адрес сервиса
и публичный сертификат `data/tls-cert.pem`; на клиентском устройстве нужно
доверять сертификату (для CLI — `--cacert data/tls-cert.pem`). Не предлагать
отключать проверку TLS. При смене LAN-адреса требуется обновить SAN сертификата
(`day-30/README.md`). Приватный ключ остаётся на сервере.

### NET-103 — сервис не открывается
Наблюдения: `ERR_CONNECTION_REFUSED`, страница входа не загружается, не
подтверждено, что Mac включён и процесс Day30 запущен.
Что делать: проверить, что Mac включён и не спит, процесс Day30 запущен
(`npm start -- --host <IP>`), порт не занят другим процессом. Ollama должна
работать на `127.0.0.1:11434`; при её отсутствии запускается отдельно
(`../day-26/run-server.sh`). Пока запуск не подтверждён, причина остаётся
предположением. В Day30 сетевые сбои в интерфейсе описываются сообщением
«Не удалось подключиться к сервису. Проверьте сеть, запуск сервера и доверие
HTTPS-сертификату.» (`failureMessage`).

### INFO-104 — «не работает авторизация», деталей нет
У тикета `needs_details: true`. На первом обращении без истории backend не
вызывает генерацию, а возвращает `status: unknown`,
`reason: missing_ticket_details` и просьбу уточнить номер дня, адрес сервиса без
токена, точный текст ошибки и шаг воспроизведения; секреты присылать не нужно
(`day-33/backend/app.py`). После ответа пользователя с уточнениями (история
тикета) запрос проходит обычный путь RAG + DeepSeek. Тест
`test_scoped_context_and_fresh_selection` фиксирует, что для INFO-104 источники
пусты и генерация не вызывается.

## 4. Ограничения и типичные ошибки API

- 422 — неверный ввод: пустой вопрос, история не парами, история другого
  тикета, лишние поля (`AskRequest`/`Turn` в `day-33/backend/app.py`).
- 404 — неизвестный тикет.
- 409 — индекс не построен/устарел или уже выполняется другой запрос
  (одновременно допускается один запрос генерации или индексации).
- 502 — сбой DeepSeek, в том числе после одной дополнительной попытки
  исправления ответа.
- 503 — MCP недоступен, нарушена связь тикет↔пользователь, ошибка локального
  поиска или embedding-модели.

## 5. Проверка цитат и «дополнительная попытка»

Ответ строится только на точных фрагментах справки: host формирует каталог
`quote_id`, модель выбирает `quote_id` с соответствующим `source_id`, host
разворачивает его в цитату и проверяет отсутствие противоречащего `quote`
(`day-33/backend/grounded.py`, `checked_answer`). При ошибке структуры или
цитаты допускается ровно одна дополнительная платная попытка с тем же
контекстом; повторная ошибка — 502. Ошибки сети/провайдера не повторяются.
В интерфейсе успешный ремонт помечается строкой «Подтверждения ответа проверены
после одной дополнительной попытки генерации». Поля `validation.repair_attempted`
и `validation.repaired` приходят в ответе API.

Если подходящих фрагментов справки нет, ответ будет `unknown` без вызова модели
(`grounded_answer` при пустых `sources`).

## 6. Гигиена данных

- Не запрашивать и не пересылать токен, приватный TLS-ключ, пароли и данные
  клиентов. В демонстрации используются только вымышленные записи.
- История беседы хранится только в памяти вкладки, ограничена 4 полными парами
  и маркируется `ticket_id`; смешанная или немаркированная история отклоняется
  (422). Поздний ответ прежнего тикета игнорируется (`revision` в
  `day-33/frontend/src/session.js`).
- Справка ограничена тремя документами `docs/support/faq.md`,
  `docs/support/troubleshooting.md`, `docs/support/privacy.md`; после их
  изменения нужна пересборка индекса.

## 7. Что памятка не покрывает

- Она не заменяет живую проверку Day30: несколько последовательных живых
  генераций и авторизованный чат с клиентского устройства в README Day30
  отмечены как неподтверждённые.
- Проверка цитат подтверждает происхождение утверждения, а не его смысловую
  истинность.
- Реальные значения токена и сертификата в документе намеренно не приводятся.
