# День 22 — первый RAG-запрос

Учебный стенд сравнивает два **независимых** ответа DeepSeek на один вопрос.
Первый вызов получает только вопрос, второй — вопрос и найденные чанки из
локального SQLite. Оба вызова используют `deepseek-flash` (или одинаковую
модель из `DEEPSEEK_MODEL` в окружении), температуру 0, отключённое
`thinking` и лимит 400 выходных токенов. Экран показывает ответы, найденные фрагменты,
точные сообщения к модели, usage и ошибки каждого режима.

## Источник и первый запуск

Корпус — отслеживаемые README текущего проекта: корневой файл и дни 01–20.
Day 21 предоставляет общую загрузку Markdown, обе стратегии разбиения,
FastEmbed-модель и точный cosine-поиск. README дней 21–23, локальные заметки,
неотслеживаемые файлы и секреты исключены. Корпус доступен из клона без PDF.

Day 22 хранит собственный индекс `day-22/data/index.sqlite`; поиск читает
SQLite в режиме `mode=ro`. Список файлов, полные относительные пути и текст
входят в SHA-256 корпуса. Изменение README или список Git делает индекс
устаревшим. Индексы прежних книг явно отвергаются и требуют пересборки;
старые локальные файлы не удаляются. Минимум — 10 000 слов; точные значения
показывает актуальный манифест в интерфейсе.

Нужны Python 3.12, Node.js 20+ и Git. В каталоге `day-22`:

```sh
python3.12 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
npm --prefix frontend ci
cp .env.example .env
# Впишите свой DEEPSEEK_API_KEY только в локальный .env
npm run dev
```

Откройте [интерфейс](http://127.0.0.1:5188). API и Swagger —
[127.0.0.1:5021/docs](http://127.0.0.1:5021/docs). После установки зависимостей
достаточно одной команды `npm run dev`. Серверы слушают только localhost.
При первом открытии нажмите **«Построить индекс»**. Ход настоящей индексации
виден на экране. Первый запуск скачивает FastEmbed-модель в
`day-22/.cache/fastembed` (около 0,22 ГБ), затем генерация эмбеддингов идёт
локально. Интернет требуется для загрузки модели и для вызовов DeepSeek.
Загрузка модели может занять время. После сборки SQLite сохраняется между
запусками. Для повторения первого прогона можно удалить только
`day-22/data/index.sqlite` при остановленном приложении и нажать кнопку снова.

Ключ есть только в `day-22/.env`; этот файл, SQLite, модельный кэш, виртуальное
окружение и frontend-сборка исключены из Git. Ключ не включается в JSON-ответы
или экспорт результатов. Не вводите личные данные в вопрос: вопрос и
извлечённые тексты отправляются DeepSeek.

## Демонстрация

1. Покажите состояние **«Нет индекса»** и нажмите **«Построить индекс»**.
   Журнал показывает чтение корпуса, загрузку модели, оба способа разбиения,
   сохранение эмбеддингов и проверку SQLite.
2. Выберите контрольный вопрос (например, про хранение истории Day 07). Нажмите
   **«Сравнить ответы»**. Слева ответ без RAG, справа — ответ с RAG.
   Если один ответ не получен, кнопка **«Повторить неудавшийся ответ»**
   отправит только отсутствующий режим и сохранит успешный ответ.
3. Раскройте найденные чанки: для каждого видны score, источник, раздел,
   `chunk_id` и полный текст. Переключите вкладку **«Точный RAG-запрос»**,
   чтобы показать объединение вопроса и реального контекста. Во вкладке
   **«Запрос без RAG»** контекста нет.
4. Переключите `structure` / `fixed` и повторите вопрос. Оба варианта
   используют один и тот же корпус, модель и SQLite, но разные границы чанков.
5. Нажмите **«Запустить все 10»**. Прогресс идёт по вопросам; итог показывает
   долю найденных слов-фактов в ответах обоих режимов, число попаданий в
   нужный раздел и раскрываемые расхождения. Это 20 вызовов DeepSeek.
   Если отдельный вызов не завершился, нажмите **«Повторить неполные»**:
   повторятся только отсутствующие ответы, уже полученные ответы и их
   источники сохранятся. Повтор использует стратегию и top-k исходного
   прогона, даже если настройки выше были изменены. При смене модели или
   индекса начните новый полный прогон. Результат можно скачать в JSON локально.

Все десять проверочных вопросов, ожидаемые факты и разделы находятся в
[`questions.json`](questions.json). Они сверены с разделами отслеживаемых README; ответ оценивается по этим текстам. Формулировки
ожиданий короткие, а совпадение слов остаётся эвристикой.

## Как устроено сравнение

`POST /api/compare` проверяет вопрос, стратегию и top-k (1–5). Затем запрос
кодируется той же FastEmbed-моделью, что использовалась при индексации, и
Day 21 выполняет точный cosine-поиск по сохранённым векторам.

Перед cosine-поиском применяется ограничение источников из исходного вопроса.
Явные `Day 07`, `day-07/README.md`, «день 7», «в дне 7» выбирают README
указанного дня; несколько явно указанных дней объединяются. Без номера дня
поиск охватывает весь корпус. Отрицание источника и неоднозначная альтернатива
не задают ограничение; неизвестный день даёт пустое извлечение. API возвращает
`retrieval_scope` (`kind`, `sources`, `reason`), интерфейс показывает выбранные
источники. SQL ограничивает кандидатов до расчёта cosine; сами оценки не меняются.
Ограничение не использует контрольные ответы или `question_id`.
 Если индекс
отсутствует, повреждён или корпус изменился, API явно просит пересобрать его;
вымышленный RAG-ответ не создаётся. Контекст включает не более 1900 символов
каждого из максимум пяти чанков плюс `source`, `title`, `section` и
`chunk_id`. Текст источника помечен как данные, а не инструкция.

Оценка намеренно простая: нормализованный поиск заранее заданных слов и
вариантов в ответе, проверка нужного `source` и суффикса `section` среди
извлечённых чанков, наличие маркера цитаты `[1]…[5]`. Это **эвристика**, а
не проверка смысла, доказательство фактической правильности или валидности
цитирования. Если один LLM-вызов завершился ошибкой, она показывается отдельно;
пара исключается из среднего показателя. Разная генерация возможна даже при
температуре 0.

Подключение к DeepSeek использует общий HTTPX-клиент на срок жизни API,
поэтому последовательные ответы могут использовать уже открытое соединение.
При ошибке подключения или HTTP 429/503 запрос повторяется не более двух раз
с короткой паузой. Таймаут ожидания **ответа** не вызывает автоматического
повтора: неизвестно, успел ли провайдер обработать и тарифицировать запрос.
В интерфейсе отдельно указаны ошибки подключения и ожидания ответа.
Неполные пары не входят в средние показатели.

## Диагностика задержки

API возвращает `retrieval_ms` — время локального поиска, а для каждого
выполненного режима `elapsed_ms` и `prompt_chars`, в том числе при ошибке
DeepSeek. `prompt_chars` — суммарное число символов сообщений `system` и
`user`; это не число токенов. На экране рядом с ответом или ошибкой видны
эти значения и фактические `model`, `thinking`, `max_tokens`. Ключ API в
диагностику не включается.

`elapsed_ms` — длительность всего вызова DeepSeek API: соединение, ожидание
провайдера, генерация, передача ответа и возможные паузы повторов. Это не
чистое время работы модели. Увеличение top-k добавляет фрагменты в RAG prompt
и может увеличить задержку, но само по себе не объясняет каждый таймаут.
После частичного повтора времена двух режимов относятся к разным попыткам,
а `retrieval_ms` — к последнему запросу. Параметры генерации по умолчанию
не менялись.

## Проверки

```sh
.venv/bin/python -m pytest tests
npm run test:frontend
npm run build
```

Тесты используют локальные fake-эмбеддер и LLM, поэтому не требуют ключа и
не расходуют API. Интеграционный тест строит временный SQLite реальным кодом
Day 21 из отслеживаемых README временного Git-репозитория и проверяет read-only поиск. Тесты не читают
пользовательские PDF; рабочие исходники Day 21 не меняются.

## Проверенный текущий корпус

После сверки документации дней 01–20: 21 README, 180 разделов,
23 291 индексируемое слово — около 46,58 условной страницы по 500 слов.
Основные индексы дней 21–23 перестроены и имеют одинаковый SHA-256:
488 fixed и 526 structure чанков, 384-мерные векторы. SQLite integrity check
проходит во всех трёх базах. README этих трёх дней в корпус не входят.

На одном обновлённом корпусе и одинаковых десяти вопросах при top-K=5
ожидаемый файл и раздел найден для fixed в 5/10 случаев без ограничения
источника и в 7/10 с ограничением по явно указанному дню; для structure —
6/10 и 7/10 соответственно. Ожидаемые слова обнаружены в объединённом
контексте в 13/27 → 18/27 и 10/27 → 17/27 случаях. Это две эвристики поиска,
не оценка смысловой правильности ответов DeepSeek. Отдельные факты всё ещё
теряются при выборе коротких чанков, даже внутри правильного README.
Экспорт локального сравнения — `data/benchmark-scope-comparison.json`.
Живая проверка DeepSeek пока не выполнена: автоматическая проверка разрешений
требует отдельного разрешения на передачу обновлённых README внешнему API.

Проверено: 18 Python-тестов, 6 frontend-тестов, production build и запуск
обоих серверов. Визуальная проверка браузера недоступна по политике инструмента.
