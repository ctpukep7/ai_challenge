# День 14 — детерминированные инварианты

Самостоятельный учебный стенд на FastAPI, Vue и SQLite. Его главный вопрос: **какие решения агенту нельзя предлагать, даже если пользователь прямо просит о них?**

## Отличие от соседних дней

- Day 13 демонстрирует конечный автомат, этапы, checkpoint, паузу и продолжение.
- Day 14 намеренно не показывает и не использует автомат. Он проверяет содержательную допустимость структурированного предложения до модели.
- Day 15 будет решать, выполнены ли prerequisites для перехода между этапами.

Рабочая задача Day 14 — обычный контекст из цели, ограничений, данных и открытых вопросов. У неё нет phase, pause/resume, checkpoint или переходов. Инварианты не смешиваются с профилем, диалогом, `long_term_entries` или `hard_constraints` контекста. Они находятся в отдельной таблице `invariants`; безопасный журнал проверок хранится в `invariant_check_events`.

Стенд включает четыре встроенных профиля: «Новичок», «Обычный», «Эксперт» и «Руководитель». «Обычный» активен на свежей базе и после полного reset. У каждого профиля есть собственный активный «Диалог 1». При запуске backend идемпотентно восстанавливает отсутствующие встроенные профили, не перезаписывая сохранённые настройки, историю и текущий выбор пользователя; если активного профиля нет, выбирается «Обычный».

## Rule model и preflight

Каждый инвариант содержит:

- категорию: `architecture`, `stack`, `technical_decision` или `business_rule`;
- машиночитаемые `field`, `operator`, `expected_value`;
- человекочитаемые `description`, `reason` и `compatible_alternative`;
- явный флаг `active`.

Поддерживаются операторы `equals`, `not_equals`, `one_of` и `not_one_of`. Для множественных значений используется разделитель `|`. Проверка регистронезависима и выполняется pure-функцией до основного provider-вызова.

Candidate также структурирован: `field`, `value`, `proposal`. При конфликте API возвращает `409 invariant_conflict` с ID правил, reason codes, причинами и совместимыми альтернативами. Провайдер не вызывается, а вопрос и ответ не сохраняются в чат. Совместимый candidate передаётся модели вместе с authoritative read-only snapshot активных инвариантов; snapshot и результат preflight видны в preview без скрытых рассуждений.

В интерфейсе `field` — это машиночитаемый ключ проверяемого правила, `value` — предлагаемое значение, а `proposal` — понятное человеку описание решения. Детерминированный preflight сравнивает только ключ и значение. Описание решения и вопрос передаются модели лишь после успешной проверки. Поэтому эти поля нельзя заменить одним свободным текстом: тогда backend не смог бы надёжно разрешить или отклонить предложение до вызова модели.

Стенд гарантирует только эти bounded structured rules. Он не пытается доказывать непротиворечивость произвольного естественного языка.

## Почему candidate заполняет человек

Ручные поля `field`, `value` и `proposal` — намеренное учебное упрощение. Они
делают видимым промежуточный объект, который в более автоматизированной системе
обычно формирует сам агент через structured output или tool call. Например,
свободный запрос пользователя может быть преобразован в предложение
`customer_data_destination=external_ai_service` без ручного заполнения формы.

После этого candidate всё равно проверяет не сама LLM, а отдельный
детерминированный policy layer. Он сопоставляет предложение с правилами,
разрешениями, workflow guards и ограничениями инструментов и возвращает один из
результатов: `allowed`, `rejected` или, в более сложной системе,
`needs_human_approval`. Только разрешённое действие доходит до модели или
исполняющего инструмента.

Таким образом, промышленный агент может автоматически предлагать варианты, но
не получает права самостоятельно отменять правила. Инварианты обычно заранее
задают разработчики, архитекторы, безопасность, compliance или владелец
бизнес-процесса; они хранятся в конфигурации, базе или policy engine,
версионируются и применяются ко всем релевантным действиям. В этом стенде
candidate вводится вручную исключительно для того, чтобы на видео отдельно и
однозначно показать предложение, preflight и результат enforcement.

## Запуск

Требуются Python 3.11+ и Node.js 20+.

```bash
cd day-14
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
npm install
npm --prefix frontend install
cp .env.example .env
npm run dev
```

- интерфейс: `http://localhost:5180`
- API: `http://localhost:5013`
- SQLite: `day-14/data/memory.sqlite3`

## Трёхминутный сценарий

Источник демонстрационного контекста задачи — объект `backendDemoTask` в `frontend/src/demo-presets.js`. Он нейтрален к выбору backend-фреймворка: требует сохранить API, данные и frontend, но не запрещает смену FastAPI. Запрет или разрешение конкретного решения задаёт только выбранный инвариант. Функция `fillDemoTask` переносит объект только в локальный `taskForm`: сетевого запроса и сохранения по этой кнопке нет.

Selector в левой панели предлагает два независимых сценария, используя одни и те же три кнопки черновиков:

- «Стек FastAPI»: `backend_framework equals fastapi`; конфликт — Node.js, совместимое решение — FastAPI.
- «Приватность данных»: `customer_data_destination not_one_of external_ai_service|personal_email`; конфликт — внешний AI-сервис, совместимое решение — локальная обработка во внутреннем хранилище.

1. После полного reset убедитесь, что активен профиль «Обычный», рабочая задача и список инвариантов пусты.
2. Оставьте в selector сценарий «Стек FastAPI». Нажмите «Заполнить рабочую задачу». Проверьте нейтральную цель: улучшить поддерживаемость backend, сохранить API, данные и frontend; текущий FastAPI + SQLite указан только как исходное состояние.
3. Отдельно нажмите «Сохранить контекст». Теперь четыре поля хранятся в SQLite и передаются агенту как рабочий контекст.
4. Нажмите «Заполнить инвариант». Кнопка только заполнит черновик правила `backend_framework equals fastapi`.
5. Проверьте форму и отдельно нажмите «Сохранить инвариант».
6. Нажмите «Подставить конфликт Node.js». Поля candidate и запроса заполнятся без сетевого запроса.
7. Отправьте запрос. Получите structured refusal; сообщение в диалоге не появится. Backend отклонил смену стека до модели.
8. Нажмите «Подставить совместимый FastAPI» и отправьте запрос отдельно. Предложение выделить service layer проходит preflight и доходит до модели.
9. Откройте «Контекст ответа»: preview покажет allowed check, `task_context_snapshot` и read-only snapshot активного правила.
10. Отключите инвариант и повторите Node.js candidate — preflight разрешит то
    же предложение и оно дойдёт до модели. Модель не обязана одобрять миграцию:
    она может критически оценить её по оставшимся ограничениям задачи. Критерий
    успеха этого шага — зелёный preflight и появившийся ответ, а не обязательное
    согласие модели.

Для второго короткого прогона новый reset не требуется. Выберите «Приватность
данных», заполните и сохраните второй инвариант, затем повторите конфликтную и
совместимую проверки. `external_ai_service` будет отклонён, а
`internal_storage` пройдёт preflight. Заголовок, подписи кнопок и пять шагов
слева меняются вместе с selector. В результате список одновременно показывает
два независимых правила и их активность.

Маршрут демонстрирует границу ответственности: рабочая задача объясняет, что требуется сделать, а отдельный инвариант детерминированно определяет, какие варианты решения допустимы ещё до вызова модели.

## Проверенный демонстрационный прогон

Финальный беззвучный сценарий проверен по HTTP-журналу и SQLite. После полного
reset встроенные профили и сессии получили ID 1–4, инварианты — ID 1 и 2, а
журнал проверок — ID 1–5. Зафиксирована последовательность:

1. `backend_framework=nodejs` — `rejected`, нарушен инвариант `#1`;
2. `backend_framework=fastapi` — `allowed`, сохранён ответ модели;
3. после отключения `#1` тот же `backend_framework=nodejs` — `allowed`, сохранён
   ответ модели;
4. `customer_data_destination=external_ai_service` — `rejected`, нарушен
   инвариант `#2`;
5. `customer_data_destination=internal_storage` — `allowed`, сохранён ответ
   модели.

В результате в audit пять проверок, но в диалоге только три разрешённые пары
user/assistant (шесть сообщений). Отклонённые попытки не записаны в чат.
`invariant_snapshot` разрешённых ответов содержит соответственно одно активное
правило, пустой список после отключения `#1` и правило приватности `#2`.
`PRAGMA integrity_check` возвращает `ok`.

## API

- `GET /api/state` — state, инварианты и безопасный журнал проверок;
- `POST /api/invariants` — создать инвариант (до 20);
- `PUT /api/invariants/{id}` — заменить структурированное правило;
- `PATCH /api/invariants/{id}/active` — явно включить или отключить;
- `DELETE /api/invariants/{id}` — удалить;
- `POST /api/ask` — preflight candidate и, только если он allowed, запрос модели;
- API профилей, памяти и сессий сохранено; `PUT /api/task` хранит только обычный контекст задачи из четырёх полей.

Очистка одного диалога не удаляет инварианты. Полный reset удаляет пользовательские профили и данные, инварианты и их audit, сбрасывает SQLite sequences приложения, затем восстанавливает четыре встроенных профиля и чистую задачу; активным снова становится «Обычный». Поэтому встроенные профили получают ID 1–4, их первые сессии — ID 1–4, а новый инвариант и первая проверка снова начинаются с ID 1. Все сохраняемые поля проходят лимиты, валидацию и запрет secret-like токенов `sk_…`/`sk-…`.
