# День 18. Планировщик и фоновые задачи

Периодический сбор погоды по поручению в чате. Пример: **«Каждые полчаса собирай погоду в Омске»**.
DeepSeek загружает skill, находит город через MCP и сохраняет расписание в SQLite.
Системный cron раз в минуту запускает того же Python-агента. Агент выбирает
наступившие задания, обращается к DeepSeek, получает погоду через MCP и сохраняет
реальное наблюдение. Вкладка **«Данные»** показывает накопленные записи.

Реализован один сценарий задания — периодический сбор данных. Напоминаний,
текстовых сводок и инструмента summary здесь нет. «Агрегированный результат» —
собранный набор наблюдений: общее количество, последнее наблюдение и записи.

## Установка и запуск

Нужны Python 3.11+ и Node.js 20.19+ (или 22.12+). Все команды из `day-18`:

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
npm install
npm --prefix frontend install
cp .env.example .env
```

В собственном `day-18/.env` укажите `DEEPSEEK_API_KEY`. Не копируйте ключи в чат,
код или Git. Модель по умолчанию `deepseek-flash`, мышление явно выключено.
`DEEPSEEK_MODEL` позволяет выбрать другой совместимый с tool calls DeepSeek model;
`DAY18_TIMEZONE` задаёт часовой пояс расписаний по умолчанию (Asia/Omsk).

```bash
npm run dev
```

Интерфейс: <http://127.0.0.1:5184>. API: <http://127.0.0.1:5017>.
Эта команда запускает веб-приложение. Она не устанавливает cron и не выполняет
фоновые задания. Без ключа интерфейс и просмотр записей работают, чат объясняет
ошибку настройки без вымышленных результатов.

## Создать расписание и проверить сбор

1. В чате напишите: «Каждую минуту собирай погоду в Омске, Россия».
2. Агент загрузит `periodic-weather-collection`, найдёт город и вызовет
   `create_weather_schedule`. Проверьте карточку задания и следующий запуск.
3. Дождитесь назначенной минуты и выполните один запуск вручную:

   ```bash
   npm run agent:run
   ```

4. Откройте «Данные»: появится температура °C, влажность %, ветер км/ч и время
   измерения. История запуска показывает вызовы MCP. Ошибка сети/модели сохраняется
   как неудачный запуск, без выдуманного наблюдения.
5. Кнопки карточки или поручения в чате ставят задание на паузу, продолжают или
   удаляют. Продолжение назначает будущий запуск; удаление окончательное.

Для управления существующим сбором можно написать:

- «Прекрати шедулинг погоды в Омске» — пауза; расписание можно продолжить.
- «Возобнови сбор погоды в Омске» — новый будущий запуск.
- «Удали крон задачу для Омска» — расписание переносится в удалённые.

Перед каждым изменением агент загружает skill и актуальный список расписаний.
Если подходят несколько заданий, он должен уточнить город или период.
При единственном текущем задании достаточно «удали задачу»; «останови все
расписания» разрешает изменить несколько конкретных заданий.
Удаление сохраняет погоду, историю запусков и JSON-запросы. Возобновить удалённое
нельзя: для нового сбора нужно создать новое расписание. Системный cron остаётся
общим диспетчером и продолжает обслуживать другие задания.

Можно попросить «Каждый день в 20:00 по Asia/Omsk собирай погоду в Омске».
Поддерживаются целые интервалы от 1 до 1440 минут или стандартный числовой cron
из пяти полей (например `0 20 * * *`). Не поддерживаются секунды, `@daily`,
буквенные дни/месяцы, `H/R/L/#`. До трёх активных или приостановленных заданий.
За одно сообщение создаётся одно расписание; неоднозначный город нужно уточнить.

## Демонстрация с установленным cron

1. Откройте интерфейс и покажите статус «Cron установлен» и инструкцию агента.
2. Отправьте: «Каждую минуту собирай погоду в Омске, Россия. Часовой пояс Asia/Omsk».
3. Покажите карточку расписания, следующий сбор и «Действия агента»:
   загрузку skill, поиск города и создание расписания через MCP.
4. Через 1–2 минуты откройте «Данные»: появится первая погодная запись.
5. Дождитесь следующей записи, покажите увеличение количества и время получения.
   Погода за минуту может не измениться — отдельные сборы различаются временем.
6. В «Последних запусках» раскройте получение и сохранение погоды через MCP,
   затем «JSON-запросы»: покажите обращения к модели, вызовы инструментов и ответы.
7. Попросите в чате «Приостанови сбор погоды в Омске», проверьте статус «Пауза».
   Затем «Возобнови сбор погоды в Омске» — появится новый будущий запуск.
8. После демонстрации удалите расписание кнопкой или поручением
   «Удали расписание сбора погоды в Омске». Оно появится в удалённых;
   собранные данные и история сохранятся.

Ручной `agent:run` для этого сценария не нужен. Оставьте компьютер включённым
и подключённым к сети до завершения демонстрации.

## Системный cron

Сначала проверьте конкретную команду и текущее состояние:

```bash
npm run cron:show
npm run cron:status
```

Установка — отдельное явное действие владельца компьютера после проверки строки:

```bash
.venv/bin/python scripts/cron.py --install
```

Удалить только запись этого приложения, сохранив остальные задания cron:

```bash
python3 scripts/cron.py --remove
```

Helper использует абсолютные пути, собственный маркер проекта и сохраняет
посторонние строки crontab. По умолчанию он только показывает команду.
Cron запускает `backend.runner --run-due --quiet` раз в минуту и подавляет вывод;
постоянно растущий лог не создаётся. Диагностика запусков хранится в SQLite и
видна в интерфейсе. Ручной `agent:run` возвращает JSON с результатами выполнения
и накопленными записями. Пустой tick обновляет отметку запуска без обращения к LLM.

Для работы 24/7 нужен включённый компьютер/сервер, работающий cron, доступ к
DeepSeek и Open-Meteo. На спящем Mac cron не собирает погоду. После пробуждения
просроченные периоды объединяются в одно текущее наблюдение, а следующий запуск
назначается в будущем. Историческая погода не придумывается. На macOS также
возможен launchd; приложение не устанавливает системные службы автоматически.

## Как это устроено

```text
Чат → общий AgentRuntime → DeepSeek → MCP stdio → расписание в SQLite
Cron → тот же AgentRuntime → DeepSeek → MCP погода → сохранение в SQLite
Vue «Данные» → FastAPI → накопленные записи SQLite
```

Skill находится в `skills/periodic-weather-collection/SKILL.md`. В режиме чата
есть каталог и явная загрузка через MCP `load_skill`; модель обязана загрузить
инструкцию до изменения заданий. Во время фонового запуска используется сохранённая
в задании версия skill с SHA-256, исходное поручение и закреплённый город.
Смена файла skill не меняет уже сохранённые задания.

В системном cron установлена одна общая запись, которая проверяет SQLite раз
в минуту. Город, периодичность и время следующего сбора хранятся в заданиях базы.
Когда срок наступает, Python собирает для модели новый контекст: режим выполнения,
сохранённый skill, исходное поручение, параметры задания и описания двух инструментов.
История чата в фоновый запуск не передаётся. Между запусками постоянного worker нет.
Из-за минутной проверки фактический старт может быть позже назначенной секунды.

MCP действительно выполняет `initialize`, `tools/list`, `tools/call` по stdio.
Инструменты диалога: `load_skill`, `resolve_city`, `create_weather_schedule`,
`list_schedules`, `set_schedule_status`, `delete_weather_schedule`.
При запуске расписания доступны только
`get_current_weather` и `save_weather_result`. Модель не получает shell-инструмент
и не пишет произвольный crontab. Город фонового вызова закреплён сервером.
`save_weather_result` принимает идентификатор реально полученного наблюдения,
а не придуманный моделью JSON.

Источник — [Open-Meteo](https://open-meteo.com/en/docs): текущие модельные погодные
данные, которые не являются показанием личной метеостанции. Отдельный ключ для
погодного API не требуется. Координаты выбираются один раз через геокодинг.
Все даты хранятся в UTC; интерфейс показывает часовой пояс задания.
Проверяются единицы, числовые диапазоны и свежесть ответа источника.

SQLite по умолчанию `data/weather.sqlite3`. `DAY18_DB_PATH` позволяет задать
отдельный абсолютный путь. Сохраняются расписания, запуски, наблюдения, сообщения
и последний tick. `.env`, окружение, базы, логи и `node_modules` исключены из Git.
Каждый запуск ограничен 8 шагами модели, 1200 output tokens на запрос и 90 секундами.
HTTP-соединение с DeepSeek переиспользуется между шагами одного запуска и закрывается
при завершении или отмене. На запрос допускается не более одного сетевого повтора:
тайм-аут соединения — 20 секунд, ожидания ответа — 45 секунд; общий лимит 90 секунд
сохраняется. MCP-изменения не повторяются при сетевой ошибке модели. Если расписание
уже сохранено, чат подтверждает его по журналу SQLite, даже когда завершающий ответ
DeepSeek не пришёл. Ошибки соединения, ключа, баланса и ограничения запросов
показываются отдельно, без исходного текста ответа провайдера.
Источник погоды ограничен 15 секундами на операцию. Только GET-запросы к Open-Meteo
при ошибке соединения, тайм-ауте или ответе 5xx допускают один повтор в пределах
этого лимита; тайм-аут соединения — 5 секунд, ожидания ответа — 8 секунд.
Неверные данные и ответы 4xx не повторяются. Аренда задания — 180 секунд. SQLite
транзакционно защищает от перекрытия cron-процессов, старых исполнителей, повторных
сохранений, паузы и отмены. Запрос чата имеет UUID, lease и восстановление уже
сохранённого действия после прерванного ответа. Пауза/отмена отзывает текущую аренду.
Успех фонового запуска требует подтверждённой записи в SQLite.

## Диагностика

В новых ответах агента и истории фоновых запусков есть раскрываемый блок
«JSON-запросы». Он показывает тело обращения к DeepSeek и нормализованное
сообщение ответа, а также MCP `tools/call` с аргументами и результатом. Это
отдельный диагностический журнал; существующий список действий агента сохранён.
JSON загружается только при раскрытии блока, поэтому обычное обновление страницы
не передаёт все тела запросов. Старые записи остаются без выдуманных запросов.
Длинные строки запросов и ответов переносятся по ширине блока;
для больших тел остаётся вертикальная прокрутка.

HTTP-заголовки, ключ доступа, служебные токены и локальные пути не отображаются.
Ошибки провайдера заменяются безопасным пояснением. Диагностическая копия каждого
тела ограничена 64 КБ; большие тела содержат отметку усечения и короткий preview.
Это ограничение не меняет отправляемый запрос. Журнал отражает вызовы runtime;
сетевой повтор SDK использует то же тело и не создаёт дополнительный шаг.

Точное число потраченных токенов пока не сохраняется: журнал содержит сообщение
модели, но не поле `usage` ответа DeepSeek. `max_tokens: 1200` — предел генерации
одного ответа, а не фактический расход. Вызовы MCP сами не расходуют токены модели,
но их результаты передаются в следующий запрос DeepSeek и входят в его контекст.

Если источник погоды недоступен, запуск отмечается ошибкой без выдуманного
наблюдения; активное расписание остаётся для следующего периода. Журнал хранит
безопасное пояснение ошибки. Исходные сетевые исключения и HTTP-коды не сохраняются,
поэтому по старому журналу нельзя точно различить тайм-аут и ошибочный HTTP-ответ.

## Что остаётся локально

В Git входят исходники, skill, тесты, инструкции и lock-файлы зависимостей.
В `.env.example` ключ пустой. Настоящий `.env`, SQLite с поручениями и JSON-журналами,
файлы базы WAL/SHM, логи, виртуальное окружение, зависимости и сборка исключены
через `.gitignore`. Демонстрационные видео также исключены общими правилами репозитория.
Не добавляйте исключённые файлы принудительно через `git add -f`.

Во время работы приложения контекст и результаты инструментов отправляются
DeepSeek, а координаты города — Open-Meteo. Это отдельные API-запросы приложения;
локальная база и ключ не должны входить в Git-коммит.

## API и проверки

- `GET /api/state` — задания, последние 100 наблюдений/запусков/сообщений, конфигурация
  без ключей и состояние cron; `has_json_requests` у сообщений и запусков.
- `GET /api/messages/{id}/requests` — `{requests}` для одного ответа агента.
- `GET /api/runs/{id}/requests` — `{requests}` для одного фонового запуска.
- `POST /api/chat` — `{prompt, request_id}` с UUID для повторной отправки.
- `POST /api/jobs/{id}/status` — `{status}` через настоящий MCP.
- `POST /api/jobs/{id}/delete` — архивирует расписание через MCP, возвращает `{state}`.
- `GET /api/samples?job_id=...` — `{count, latest, records}` (последние 100 записей).
- `GET /api/skill` — `{content}` для просмотра учебной инструкции.

Полный архив остаётся в SQLite; интерфейс показывает последние 100 наблюдений.
Состояние cron «неизвестно» означает, что ОС не позволила прочитать crontab,
а не отсутствие расписания. Последний tick показывает фактический запуск агента.

```bash
npm test
npm run build
```

Тесты используют отдельные временные базы и fake LLM/погодный источник.
Проверяются реальные MCP subprocess, загрузка skill, tool calls, расписания,
часовой пояс, идемпотентность, lease recovery, пауза/отмена, ошибки источника,
защита от поддельного результата и отсутствие LLM-вызовов при пустом tick.
Это не live-проверка платного DeepSeek API.

Первичные источники:
[DeepSeek Tool Calls](https://api-docs.deepseek.com/guides/tool_calls/),
[DeepSeek Harness skills](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/skills.md),
[MCP Python SDK](https://github.com/modelcontextprotocol/python-sdk),
[croniter](https://github.com/pallets-eco/croniter).
