# День 20 — Orchestration MCP

Агент планирует поездку по реальному почасовому прогнозу и свободному времени
в личном Яндекс Календаре. Он сам выбирает инструменты трёх MCP-серверов,
сохраняет проверенный проект и объясняет результат. Русский интерфейс показывает
чат, обнаруженные инструменты, последовательную трассу и карточки планов.

## Настройка и запуск

Нужны Python 3.11+, Node.js 20.19+ и доступ к DeepSeek, Open-Meteo и Яндекс CalDAV.
Из папки `day-20` один раз установите зависимости:

```sh
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
npm --prefix frontend ci
cp .env.example .env
```

В собственном `.env` укажите `DEEPSEEK_API_KEY`, `YANDEX_CALDAV_USERNAME`
и `YANDEX_CALDAV_APP_PASSWORD`. Для календаря нужен отдельный пароль приложения
Яндекса с доступом к календарю. Пароль обычного входа использовать не нужно.
Адрес по умолчанию — `https://caldav.yandex.ru`. Настройка описана в
[официальной инструкции Яндекса](https://yandex.ru/support/yandex-360/customers/calendar/web/ru/data-exchange/synchronization/sync-desktop).

Запуск одной командой:

```sh
npm run dev
```

Откройте [интерфейс](http://127.0.0.1:5186).
Backend: [127.0.0.1:5019](http://127.0.0.1:5019/docs).
Остановка — Ctrl+C. По умолчанию используется `deepseek-flash`, thinking выключен,
часовой пояс `Asia/Omsk`. `.env`, SQLite, виртуальное окружение, зависимости и
сборка исключены из Git. API рассчитан на локальное использование одним владельцем.

## Демонстрация

Кнопка «Поездка по погоде» только заполняет поле ввода. Отправьте запрос:

> Найди время для трёхчасовой поездки в Омске в ближайшие семь дней, между
> 10:00 и 18:00 по омскому времени. Нужно не ниже +5 °C, вероятность осадков
> до 30% и ветер до 8 м/с. Проверь мой календарь, сохрани план и предложи событие.

Все уточнения выполняются в чате. Если календарей несколько, ответьте его полным
названием, например «Используй календарь “Личный”», или точным ID. Первый календарь
автоматически не выбирается. При одинаковых названиях агент уточнит ID;
неоднозначные ответы, номера и опечатки требуют уточнения полного имени.
Город, регион и недостающие условия также указываются обычным сообщением.
Агент продолжает поручение по истории диалога и заново проверяет источники.

При потерянном ответе повтор того же сообщения использует прежний UUID,
чтобы не запускать флоу дважды. Выбор календаря текстом разрешает чтение;
запись события по-прежнему требует отдельного подтверждения готовой карточки.

При наличии подходящего времени ожидаются минимум шесть вызовов:

1. `weather__resolve_city` — обнаружить город.
2. `calendar__list_calendars` — получить доступные календари.
3. `calendar__find_free_slots` — проверить свободное время выбранного календаря.
4. `weather__get_hourly_forecast` — получить почасовой прогноз.
5. `plans__save_trip_draft` — сохранить проект с настоящими идентификаторами обоих источников.
6. `plans__get_trip_plan` — прочитать сохранённый проект для ответа.

Независимые чтения погоды и календаря могут менять порядок. Прогноз всегда
следует после обнаружения города, доступность — после списка календарей,
а сохранение — после обоих источников. При отсутствии подходящего времени
проекта не будет: агент должен объяснить, какие условия не выполняются.
Доступный диапазон дат определяется фактически возвращённым прогнозом.

Проверьте карточку: город, название, календарь, начало, окончание и часовой пояс.
«Подтвердить и создать событие» разрешает запись именно этих полей.
«Отклонить» завершает проект без календарной записи. Текстовое «да» в чате
событие не создаёт. Изменение времени или календаря требует нового проекта.

Примеры «Только погода» и «Только календарь» позволяют отдельно проверить
выбор нужного MCP-сервера. В трассе видны порядок, инструмент, безопасные
аргументы, длительность, краткий результат и ошибка. Личные названия встреч,
описания, исходный CalDAV, ключи и внутренние рассуждения не отображаются.

Чат поддерживает Markdown в сообщениях пользователя и агента: заголовки,
выделение, списки, цитаты, таблицы, ссылки и блоки кода. Исходный HTML отображается
как текст; изображения из сообщений автоматически не загружаются.

Как в Day 18, строка «JSON-запросы» под ответом агента раскрывает обмены
именно этого запроса. Если ответ ещё не получен или запуск завершился ошибкой,
JSON доступен под сообщением пользователя. Для модели сохраняется фактическое
сериализованное тело HTTP-запроса; для MCP — параметры `tools/call` с исходным именем инструмента и нормализованный
ответ SDK. Видны порядок, `tool_call_id`, связь с шагом трассы, длительность
и ошибка. Вызов подтверждения карточки также появляется здесь.
Шаги идут последовательно, с JSON запроса и ответа под каждым шагом.
Просмотр встроен в чат; длинные строки переносятся, тела имеют свою прокрутку.
Выбор другой трассы не меняет JSON открытого сообщения.

Снимки сохраняются отдельно в SQLite и доступны после перезагрузки. Просмотр
загружает их только при раскрытии и обновляет во время выполнения. Ключи,
заголовки авторизации, служебные пути, приватные поля встреч и внутренние
рассуждения исключаются до сохранения. Размер снимков ограничен; сокращение
помечается. HTTP-заголовки и MCP transport id не показываются. Для старых запусков
без снимков выводится пояснение; запросы не восстанавливаются из трассы.

## Как устроена оркестрация

Три отдельных процесса общаются с backend по `stdio` через официальный Python
MCP SDK. Каждый проходит `initialize` и все страницы `tools/list`. Обнаруженный
каталог передаётся модели на каждом шаге. Реестр сохраняет точное соответствие
`server_id__tool_name` исходному имени, JSON Schema и MCP-сессии; одинаковые
имена на разных серверах не конфликтуют.

Модель → выбранный MCP-инструмент → результат с исходным `tool_call_id` → модель.
Backend проверяет аргументы и ограничения, но не выполняет недостающие шаги
вместо модели. Все вызовы последовательные. Лимиты: 12 обращений к модели,
20 вызовов инструментов, до трёх в одном ответе и 180 секунд на запуск.
После ошибки аргументов разрешены две последовательные попытки исправления.
Незавершённый запуск имеет видимый статус и сохраняет частичный проект.

Weather получает данные Open-Meteo. Calendar читает CalDAV и возвращает только
свободные интервалы. Plans работает с локальной SQLite, без произвольных путей
и файловых инструментов. Идентификаторы результатов привязаны к запуску:
выдуманные, устаревшие и чужие источники не подходят. Сохранение проверяет
длительность, доступность и погоду на всём выбранном интервале.

Сессиями владеет одна coroutine с общим `AsyncExitStack`: открытие и закрытие
в обратном порядке происходят в той же задаче. Ключ DeepSeek остаётся в backend,
календарные credentials передаются только Calendar.

При поручении проверить календарь модель DeepSeek получает названия доступных
календарей и свободные интервалы. Названия и описания личных встреч остаются
внутри Calendar; в ответ модели и трассу они не попадают.

## Запись и восстановление

`create_trip_event` обнаруживается, но скрыт от модели. Его вызывает только
обработчик подтверждения, а Calendar дополнительно проверяет сохранённое approval
и неизменность полей. Перед записью занятость проверяется повторно. Новый конфликт
требует нового плана и нового согласия.

Операция и устойчивый UID сохраняются до внешнего вызова. Повторное и одновременное
подтверждения не создают новые операции. При потерянном ответе выполняется поиск
по UID и сравнение полей. Кнопка «Сверить событие» только проверяет неопределённый
результат; слепого повторного создания нет. Если UID не найден после неопределённой
записи, нужна ручная сверка календаря. Проверка занятости и создание не являются
атомарной операцией CalDAV: внешнее изменение между ними остаётся возможным.

Повтор UUID `request_id` возвращает тот же запуск; изменение запроса с тем же UUID
отклоняется. После перезапуска прерванные запросы получают `interrupted`, а
прерванная запись — `uncertain`. История, трассы и проекты сохраняются в SQLite.

## Границы реестра и доказательств в Дне 20

В Дне 20 backend держит три stdio MCP-сессии на время работы API:
Weather, Calendar и Plans. Он получает все страницы `tools/list`,
отклоняет повторяющийся cursor и сохраняет привязку alias к исходному
имени инструмента, схеме и конкретной сессии. Alias `weather__resolve_city`
используется моделью; на проводе MCP отправляется исходное `resolve_city`
в Weather. Такая привязка допускает одинаковые исходные имена на разных
серверах без маршрутизации по догадке.

JSON Schema проверяется до отправки вызова. Если инструмент требует
`run_id`, реестр сам добавляет текущий ID; модель не вправе передать
или подменить его. Каталог модели включает все обнаруженные инструменты
кроме `create_trip_event`. Таким образом, наличие инструмента записи
в registry для диагностики не означает его доступность в обычном
цикле выбора инструментов.

### Контекст, ограничения времени и сохранение проекта

День 20 передаёт модели system-инструкцию, текущее время в настроенном
поясе, до шести ранее завершённых пар сообщений и новый запрос пользователя.
История помогает продолжить уточнение, но старые tool IDs в неё не
переносятся: прогноз, каталог календарей и доступность получают заново
для текущего запуска. `TIMEZONE` задаёт default `Asia/Omsk`,
`DEEPSEEK_MODEL` — default `deepseek-flash`, `DAY20_DB_PATH` — путь отдельной
SQLite-базы. Запрос пользователя ограничен 5000 символами.

Параметры вызова модели Дня 20: температура 0,2, thinking disabled,
HTTP timeout 40 секунд, автоматические SDK-повторы отключены.
Явный `max_tokens` в этом вызове не устанавливается. Отдельный MCP-вызов
по умолчанию ограничен 35 секундами, весь агентный запуск — 180 секундами.
Эти сроки ограничивают ожидание и число шагов, но не являются измерением
стоимости или гарантией скорости внешнего провайдера.

`find_free_slots` проверяет положительную длительность до 24 часов и
диапазон не длиннее 16 дней. Дневное окно должно закончиться в тот же
день; пересекающее полночь окно не поддерживается. Свободный слот —
доступный интервал, который может быть длиннее желаемой поездки.
При сохранении проект должен выбрать внутри него интервал ровно
проверенной длительности с будущим началом. Граница конца исключительна:
неподходящий час, начинающийся ровно после завершения поездки,
не относится к её погодному покрытию.

В Дне 20 температура сравнивается в °C, вероятность осадков — в процентах,
ветер — в м/с. Каждый перекрывающий поездку час должен присутствовать
в прогнозе, содержать конечные числовые значения и удовлетворять переданным
ограничениям. Пропуск часа или неполные данные блокируют сохранение.
Backend проверяет структурированные параметры и источники; интерпретация
свободного текста пользователя остаётся задачей модели. Поэтому перед
подтверждением нужно сверить условия проекта с исходным поручением.

### Подтверждение и сверка события Дня 20

Проект `draft` не является календарной записью. Подтверждение карточки
сохраняет `approved_at`, UID и hash точных полей события в operation;
MCP Calendar повторно сравнивает их с проектом. Текст чата «да» не создаёт
этого approval. Статус `created` подтверждается созданием или нахождением
существующего события по тому же UID и совпадающим полям.
`conflict` означает, что время уже прошло либо занятость изменилась;
нужны новый проект и новое подтверждение.

Статус `uncertain` в Дне 20 сохраняет неясный исход внешней операции.
Повтор endpoint confirm для такой карточки выполняет только lookup UID:
если событие найдено и поля совпадают, состояние становится created;
если не найдено или поля отличаются, новая запись запрещена и требуется
ручная сверка. Это отличается от Дня 17, где неизвестный исход остаётся
для ручной проверки без автоматического lookup. Calendar не возвращает
в модель описания и названия личных встреч: в модель идут названия
календарей и вычисленные свободные интервалы.

## API и проверки

| Метод | Назначение |
| --- | --- |
| `POST /api/chat` | `prompt`, UUID `request_id`, необязательный `calendar_id` → `run_id` |
| `GET /api/runs/{id}` | Статус, трасса, ответ и проект; интерфейс опрашивает раз в секунду |
| `GET /api/runs/{id}/json-requests` | Сохранённые безопасные JSON-снимки запуска сообщения |
| `GET /api/state` | Сообщения, каталог, планы, календари и история запусков |
| `POST /api/plans/{id}/confirm` | Подтвердить неизменяемую карточку / сверить UID |
| `POST /api/plans/{id}/reject` | Отклонить проект без внешней записи |

```sh
npm test
npm --prefix frontend test
npm run build
```

Тесты используют временные базы и синтетические источники; ключи не нужны,
реальных записей в календаре нет. Интеграционные проверки запускают настоящие
stdio MCP-процессы и scripted-модель, проверяют зависимости и возврат результатов
с правильными ID, маршрутизацию, ошибки источников, погодные ограничения и
безопасное подтверждение. Отдельные CalDAV-тесты проверяют повторения,
целодневные события, часовые пояса и исключительные границы интервалов.
Проверки JSON используют настоящий HTTP-клиент SDK с синтетическим transport:
сопоставляют сериализованное тело, проверяют скрытие секретов до SQLite,
отмену, перезапуск, параллельные операции и отсутствие вымышленных записей.
Frontend-тесты проверяют Markdown и безопасную обработку HTML, ссылок и изображений,
а также привязку JSON к сообщению и обновление именно его запуска и подтверждения.

Первичные источники: [MCP Tools](https://modelcontextprotocol.io/specification/2025-06-18/server/tools),
[Open-Meteo](https://open-meteo.com/en/docs),
[python-caldav](https://caldav.readthedocs.io/stable/caldav/collection.html).
