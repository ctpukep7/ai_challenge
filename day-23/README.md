# День 23 — фильтрация релевантности и query rewrite

Стенд сравнивает обычный RAG, фильтрацию найденных чанков и переписывание
поискового запроса с фильтрацией. Интерфейс показывает исходный и изменённый
запросы, реальные cosine-оценки, решения по каждому кандидату, конечный контекст
и точные сообщения, отправленные DeepSeek.

## Запуск

Нужны Python 3.12, Node.js 20+, Git и текущий checkout проекта.
Корпус — корневой `README.md` и отслеживаемые Git файлы `day-01/README.md` … `day-20/README.md`.
Файлы читаются из рабочей папки; PDF и подготовка книжного корпуса не требуются.
README дней 21, 22 и 23 исключены, чтобы инструкции RAG-стендов и результаты
их проверки не становились источником собственных ответов. Локальные wiki, Memory Bank,
отчёты, `.env` и Markdown из зависимостей в корпус не входят.

В каталоге `day-23`:

```sh
python3.12 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
npm --prefix frontend ci
cp .env.example .env
# Для генерации ответов и LLM rewrite впишите DEEPSEEK_API_KEY в локальный .env.
npm run dev
```

Откройте [интерфейс](http://127.0.0.1:5189/). API и Swagger:
[127.0.0.1:5022/docs](http://127.0.0.1:5022/docs). Оба сервера слушают только
localhost; остановка — `Ctrl+C`. После установки достаточно `npm run dev`.

При первом запуске нажмите «Построить индекс». Day 23 читает README проекта
и сохраняет свой `data/index.sqlite`. Соседние дни запускать не требуется.
Из Day 21 используются библиотечные функции чтения Markdown, chunking,
эмбеддингов и SQLite; загрузчик PDF-корпуса не используется. Индекс содержит
обе стратегии `fixed` и `structure`, многоязычную FastEmbed-модель и
384-мерные векторы. При первом использовании модель скачивается в собственный
`.cache/fastembed`; дальнейшие поиск и локальный rewrite работают без внешнего API.

Список источников виден в интерфейсе. Для каждого чанка сохраняются полный
путь относительно репозитория (`day-17/README.md`), заголовок, раздел и `chunk_id`.
При изменении текста или списка README индекс становится устаревшим:
нажмите «Построить индекс» ещё раз. Старый книжный индекс также требует
перестроения; он не используется для нового корпуса.

## Три режима

- **Обычный RAG:** исходный запрос → `top_k_before` кандидатов → первые
  `top_k_after` в контекст, без порога.
- **Фильтр:** тот же запрос и кандидаты → оставить `score >= threshold` →
  максимум `top_k_after` в контекст.
- **Rewrite + фильтр:** переписанный поисковый запрос → новый список
  `top_k_before` → тот же порог и конечный лимит.

Исходный вопрос пользователя для генерации ответа одинаков во всех режимах.
У обычного RAG тот же конечный лимит, чтобы эффект фильтра не смешивался с
простым изменением бюджета контекста. Ранжирование остаётся косинусным: отдельная
CrossEncoder-модель не используется; в задании реализован вариант с фильтром
релевантности.

Перед cosine-поиском применяется ограничение источников из исходного вопроса.
Явные `Day 07`, `day-07/README.md`, «день 7», «в дне 7» выбирают README
указанного дня; несколько явно указанных дней объединяются. Без номера дня
поиск охватывает весь корпус. Отрицание источника и неоднозначная альтернатива
не задают ограничение; неизвестный день даёт пустое извлечение. API возвращает
`retrieval_scope` (`kind`, `sources`, `reason`), интерфейс показывает выбранные
источники. SQL ограничивает кандидатов до расчёта cosine; сами оценки не меняются.
Ограничение не использует контрольные ответы или `question_id`.

Во всех трёх режимах сохраняется ограничение исходного вопроса, даже если
rewrite изменил номер дня. Этот выбор README предшествует сравнению режимов;
второй этап фильтрации по cosine-порогу остаётся предметом задания Day 23.


Начальные параметры — 12 кандидатов, максимум 3 фрагмента в ответе, cosine-порог
0,50. Можно менять оба top-K, порог и стратегию разбиения. Итоговый K не должен
превышать исходный. Кандидаты помечаются как выбранные, отсечённые порогом или
не попавшие в конечный top-K. В prompt входят только выбранные фрагменты с
последовательными ссылками `[1]`, `[2]`, … и метаданными.

Если контекст пуст, стенд возвращает явный отказ отвечать по базе и не вызывает
LLM для этого режима. Это **решение приложения**, а не сгенерированный моделью
ответ. Оно не доказывает, что ответ отсутствует во всех README: слишком высокий
порог может удалить полезный текст.

## Переписывание запроса

По умолчанию работает локальный rewrite: нормализация и явные правила
раскрытия сокращений/терминов, связанных с технологиями проекта. Правила не обращаются
к контрольным ответам, источникам или идентификаторам вопросов. На экране видны
новый запрос и применённые правила; если ничего не изменилось, это указано.

Вариант **через DeepSeek** делает дополнительный короткий вызов модели,
получая поисковый запрос. Вход — исходный вопрос и инструкция сохранить смысл;
ожидаемые факты и найденные чанки не передаются. Результат проверяется до
векторизации. Если модель вернула некорректный запрос или произошёл таймаут,
третий режим получает явную ошибку; результаты первых двух сохраняются.

Rewrite может улучшить терминологию запроса, сохранить её без изменений или
исказить смысл. Проверяйте показанную строку. Оценки cosine исходного и нового
запросов относятся к разным векторам, поэтому рост score сам по себе не
доказывает рост качества ответа.

## Демонстрация без голоса

1. Покажите список README-источников, готовый индекс, порог и оба top-K.
2. Выберите вопрос о работе одного из дней и выполните **только поиск**
   с локальным rewrite. Сравните исходную и переписанную строки.
3. Покажите три режима и раскрытые кандидаты: score, порог, причина отсечения,
   источник, раздел, `chunk_id` и текст. Сравните число фрагментов в контексте.
4. Измените порог и повторите поиск. При завышенном пороге станет видно, что
   полезные фрагменты тоже могут исчезнуть.
5. Выберите посторонний вопрос о погоде или рецепте. Обычный поиск всё равно
   возвращает ближайшие чанки; фильтр может оставить пустой контекст.
6. Запустите **сравнение ответов** и покажите реальные ответы, отказ приложения
   при пустом контексте, точные prompts и диагностику времени/API-вызовов.
7. Выполните общий прогон контрольного набора, сначала только поиска, затем
   при необходимости с генерацией ответов. Покажите метрики и скачайте JSON.

Результаты фоновых операций появляются по мере готовности. Кнопка остановки
прекращает следующие шаги; уже отправленный запрос DeepSeek может завершиться
и быть тарифицирован. Настройки каждого прогона сохраняются в результате,
поэтому изменение полей не меняет уже полученное сравнение.
При обновлении страницы активный прогон восстанавливается: интерфейс читает
его состояние и продолжает polling, не запускает новое сравнение или LLM-вызов.

## Контрольные вопросы и качество

[`questions.json`](questions.json) содержит 10 вопросов по README проекта и три посторонних вопроса. Для вопросов по базе указаны ожидаемые
факты, файл и раздел; для посторонних ожидается отказ **по этой базе**.

Прогон поиска с локальным rewrite не делает LLM-вызовов. Генерация всех трёх
режимов для 13 вопросов требует до 39 вызовов; при LLM rewrite дополнительно
до 13. Пустой контекст сокращает фактическое число вызовов. Перед запуском
интерфейс поясняет выбранный вариант.
Кнопки «только поиск» всегда используют локальный rewrite, даже если для
генерации выбран вариант через DeepSeek.

Счётчик отражает основные вызовы модели из приложения; короткие HTTP-повторы
при ошибках подключения/429/503 в него не входят. Это не счётчик тарифицированных
операций провайдера.

Метрики поиска показывают попадание ожидаемого раздела, долю выбранных фрагментов
из ожидаемого раздела и пустое извлечение для посторонних вопросов. Доля раздела —
только proxy: каждый его чанк не обязательно содержит ответ. Для сгенерированных
ответов используется эвристика совпадений ожидаемых слов и проверка диапазона
маркеров цитат; она не проверяет смысл или достоверность цитирования. Сравнение
ошибок отдельно от качества и указание знаменателя не позволяют выдавать
неполный прогон за успешный.

Порог настраивается под модель и новый корпус. Контрольные вопросы используются
для предварительной настройки, поэтому результаты не являются независимой
оценкой обобщения. Улучшение не гарантируется: rewrite может не изменить
запрос или ухудшить извлечение, а высокий порог — удалить полезный контекст.

## Данные и ограничения

SQLite, `.env`, кэш модели, окружение, сборка и
экспортированные результаты не коммитятся. Вопрос и выбранные отрывки
отправляются DeepSeek при явном запуске генерации; LLM rewrite отправляет
исходный вопрос. Ключ не попадает в API-ответы или JSON export.

Все режимы ответов используют одинаковую модель из `DEEPSEEK_MODEL`
(по умолчанию `deepseek-flash`), температуру 0, отключённое thinking и лимит
400 выходных токенов. Общий HTTPX-client сохраняет соединения; ограниченные
повторы применяются к ошибкам подключения и HTTP 429/503. Таймаут ожидания
ответа автоматически не повторяется: провайдер мог уже обработать запрос.
Продолжительность HTTP-вызова включает ожидание и передачу, а не только
генерацию модели.

Состояние фоновых прогонов хранится в памяти процесса и ограничено последними
20 операциями. После перезапуска сервера результаты исчезают; сохраните нужный
JSON заранее. SQLite-индекс сохраняется между запусками.

## Проверки и первичные источники

```sh
.venv/bin/python -m pytest tests
npm run test:frontend
npm run build
```

Автоматические тесты используют временный Git-репозиторий с искусственными
README и fake LLM: личные документы и API-ключ не требуются. Проверяются порог/top-K, query rewrite, состав
prompt, пустой контекст, ошибки и отмена операций, метрики и собственный индекс.
Поиск дополнительно проверяется на настоящем README-корпусе. Тесты с fake LLM
не заменяют проверку реальных ответов модели. Визуальная проверка в браузере
недоступна из-за политики инструмента.

Теория второго этапа: [Sentence Transformers](https://www.sbert.net/examples/sentence_transformer/applications/retrieve_rerank/README.html).
Поведение score-порога: [Qdrant](https://qdrant.tech/documentation/search/search/#filtering-results-by-score).
Схема Rewrite-Retrieve-Read: [Ma et al.](https://arxiv.org/abs/2305.14283).

## Проверенный текущий корпус

После сверки документации дней 01–20: 21 README, 180 разделов,
23 291 индексируемое слово — около 46,58 условной страницы по 500 слов.
Основные индексы дней 21–23 перестроены и имеют одинаковый SHA-256:
488 fixed и 526 structure чанков, 384-мерные векторы. SQLite integrity check
проходит во всех трёх базах. README этих трёх дней в корпус не входят.

Прогон 13 вопросов при 12 → 3 и пороге 0,50 выполнен без LLM-вызовов.
Попадание ожидаемого файла и раздела для fixed: 6/10 в обычном RAG,
5/10 с порогом, 4/10 после локального rewrite и порога. Для structure:
6/10, 5/10, 5/10. Порог сократил полезное извлечение: он не гарантирует
улучшения и требует проверки на собственных вопросах.

Для двух из трёх посторонних вопросов фильтр оставил пустой контекст.
Вопрос о фактической погоде на завтра находит README погодного агента,
хотя прогноза там нет. Cosine-фильтр не определяет отсутствие конкретного факта.
Экспорты: `data/benchmark-readmes-fixed.json` и
`data/benchmark-readmes-structure.json`; они не коммитятся.
Живые ответы после обновления корпуса пока не проверены: для передачи
README DeepSeek автоматическая проверка запросила отдельное разрешение.

Проверено: 66 Python-тестов, 10 frontend-тестов, production build и запуск
обоих серверов. Визуальная проверка браузера недоступна по политике инструмента.
