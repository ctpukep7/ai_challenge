# День 29 — настройка локальной LLM

Сравнение исходной и настроенной генерации одной модели
`qwen3:4b-instruct-2507-q4_K_M`. Два наглядных пресета показывают настройку
под конкретную задачу; свободный ввод и ручная форма параметров сохранены.
Старые эксперименты с отчётами, логическими пазлами и липограммой не являются
доказательством универсального улучшения.

## Соответствие заданию Day29

- **Параметры:** пресеты меняют temperature, лимит ответа `num_predict`
  и, для маршрутизации, окно контекста `num_ctx` относительно исходного варианта.
- **Prompt под задачу:** отдельные SYSTEM-инструкции для SQL-документа
  и маршрутизации; JSON Schema дополнительно задаёт структуру результата.
- **Качество до/после:** сравниваются полнота, структура и данные целевой задачи
  по одинаковому пользовательскому запросу. Содержание SQL проверяется вручную.
- **Скорость и ресурсы:** реальные метрики показываются у обоих ответов.
  Маршрутизация сокращает время готового ответа и размещение модели; SQL даёт
  полный документ за большее время. Улучшение всех показателей не обещается.
- **Квантование, условный пункт:** используется установленная Q4_K_M.
  Эксперимент с другим квантованием не проводился; наличие Q4 не считается
  сравнением квантований. Границы измерений приведены ниже.
- **Результат:** два сценария настройки локальной модели под конкретные задачи,
  без обучения весов.

Документация сверена с принятыми пресетами и живыми прогонами 12 октября 2026.
Реализация Day29 при этой перепроверке не менялась; последние 340 backend
и 59 frontend тестов и production build успешны.

## Работа

Введите вопрос и измените настройки. «Сравнить модели» даёт два свежих ответа
на одинаковый запрос; «Только настроенная модель» — один. Enter сравнивает,
Shift+Enter добавляет строку, Tab перемещает фокус. История видна в текущей вкладке,
но не передаётся модели. После перезагрузки она исчезает.

Исходный вариант фиксирован: temperature0,7, output1024, context4096,
TopK20, TopP0,8, MinP0, repeat1/window64, presence0, seed−1,
без системной инструкции, дополнительных stop и принудительного формата.
Настраиваемый вариант редактируется; SYSTEM по умолчанию пустой, seed−1 случайный.
Настройки сохраняются вместе с ответом; изменение формы не меняет прошлые результаты.

## Два сценария с заметной разницей

Пресет заполняет пример, параметры и SYSTEM. Нажмите «Сравнить модели»:
оба варианта получают один и тот же пользовательский запрос. Выбор сам ничего
не отправляет. Исходные настройки сохранены, все поля можно редактировать.

- **16 карточек SQL.** Подготовка полного JSON-документа для учебного приложения:
  16 тем, определения и практические задания. Temperature0, выход2048,
  контекст4096; SYSTEM задаёт полный документ, JSON Schema — его структуру.
  Проверяются корректность JSON, число карточек, порядок тем, номера и поля.
  Смысл SQL-объяснений проверяется вручную. Больший лимит нужен для полноты,
  поэтому ускорение на этом кейсе не обещается.
- **Маршрутизация обращения.** Двойное списание с упоминаниями доставки,
  возврата товара и запрета отменять заказ. Temperature0,1, выход256,
  контекст3072; SYSTEM превращает универсального помощника в модуль поддержки,
  а schema задаёт машинную карточку. Проверяются очередь, сумма, номер заказа,
  неизвестная дата и запрет отмены; смысл requested_action проверяется вручную.
  Исходный вариант может написать корректное письмо, но такое письмо
  не соответствует целевому контракту маршрутизатора.

Проверки оценивают конкретный контракт задачи, а не общий интеллект модели.
SYSTEM и формат входят в оптимизацию и показываются в параметрах ответа.
Schema не содержит готовых сумм, ID или текстов ответов: модель извлекает
данные из примера и применяет общие правила очередей. Нет подстановки
готового ответа или исправления JSON после генерации.

Для изменённого вопроса эталон встроенного примера не применяется: оценка
становится ручной. Предыдущие результаты сохраняют свои критерии и параметры.
Обрыв отмечается как провал полноты, неизвестные метрики — как отсутствие данных.
Один запуск не гарантирует повторяемость; память `/api/ps` не равна полному RAM.

### Квантование

Используется установленная **Q4_K_M**. На12октября2026 `/api/tags` содержит
только эту версию:2497293803байта весов. Другой вариант квантования пока
не установлен; сравнение квантований в этом стенде не выполнялось.
Новые веса не скачиваются. Параметры и SYSTEM меняют генерацию, а не квантование
и не веса. Размещение модели из `/api/ps` отличается от размера файла весов
и от полного пика RAM компьютера.

## Ручные параметры

Доступны11sampling options, SYSTEM и формат ответа:

- Temperature0–2; выход256/512/768/1024/1536/2048 токенов;
  контекст3072/4096/6144/8192. Большой контекст увеличивает расход памяти.
- TopK0–100, TopP/MinP0–1.
- Repeat penalty0,8–1,5, окно повторов0–2048; presence penalty0–2.
- Seed−1…2147483647; −1 случайный, фиксированный seed не гарантирует правильность.
- До4stop-фраз, каждая до80символов/256байт. Одна на строку, перенос кодируется
  как `\n`, возврат строки `\r`, обратный слеш `\\`. Пустые строки и повторы запрещены.
- SYSTEM до3000символов/8000байт UTF-8; можно оставить пустым.

Think удалён из редактируемых параметров. Приложение использует `think=false`,
`stream=false`, `keep_alive=1m`. Изменение параметров не обучает веса модели.

## Формат ответа

«Обычный текст» не задаёт нативный формат. «JSON» передаёт `format="json"`
в Chat API. «JSON Schema» позволяет ввести собственную JSON-схему; она передаётся
Ollama в верхнем поле `format`, отдельно от sampling options. Исходный вариант
всегда получает обычный запрос без принудительного формата.

Схема должна быть непустым JSON-объектом. Размер ограничен5000символами/12000байтами,
глубина8 и число узлов256; `$ref` не поддерживается приложением. Некорректный JSON
блокирует отправку. Ollama может отклонить неподдерживаемую схему; ошибка видна
без скрытой правки или повторного запроса. Формат ограничивает структуру ответа,
но не гарантирует правильность фактов. Ответ модели показывается без исправлений.

## Метрики и ограничения

Под обоими ответами одинаковые15строк: полное время, HTTP, прогрев,
загрузка runner при прогреве/генерации, генерация, входные/выходные/все токены,
скорость получения/генерации, размещение модели/GPU, фактический контекст
и число измерений `/api/ps`. Размер размещения не является полным пиком RAM macOS.

Одна выполняемая операция; автоматических повторов нет. Таймаут ответа120с,
сравнения240с. Вопрос до4000символов/10000байт UTF-8. При ошибке вопрос сохраняется.
Результаты экспериментов находятся в игнорируемом `data/`, не в публичном API.

### Проверка новых сценариев · 12 октября 2026

До внедрения вопросы и настройки заморожены. Каждый сценарий проверен дважды:
сначала исходная → настроенная, затем настроенная → исходная. Все восемь
ответов получены от настоящей локальной Qwen; ошибки провайдера не возникли.

- **SQL, оба прогона:** исходный ответ достиг1024токенов, оборвался и не
  разбирается как JSON. Настроенный использовал1247токенов и вернул все16карточек
  без обрезки, с правильными полями, порядком тем и номерами. Полное время:
  37,00 →59,58с и62,16 →80,81с. Скорость генерации не улучшилась. Этот кейс
  показывает полноту и пригодность документа для приложения; содержание SQL
  и качество русского языка по-прежнему требуют проверки человеком.
- **Маршрутизация, оба прогона:** исходный вариант написал письмо вместо
  JSON-карточки (270/284токена). Настроенный вернул60токенов и правильные значения
  billing/7318/2490/null/false; requested_action — возврат второго списания.
  Полное время17,18 →7,61с и17,49 →7,00с: примерно2,3–2,5раза быстрее в этих
  прогонах. Размещение модели уменьшилось на4,92% из-за окна4096 →3072.
  Здесь показана специализация под контракт поддержки, а не неспособность
  исходной модели написать корректное письмо.

Парсер интерфейса независимо проверил структуру всех сохранённых ответов.
В схеме нет готового текста карточек или фактических значений заявки.
Temperature0 у SQL даёт одинаковый настроенный ответ в двух прогонах;
это повторяемость конкретного кейса, не доказательство общего преимущества.
Время меняется с нагрузкой и прогревом. Изменение SYSTEM, schema и параметров
проверено как единый пресет; вклад каждого фактора отдельно не измерялся.
Локальные измерения: игнорируемый `data/visible-difference/`.
Браузерный прогон маршрутизации также показал письмо против корректной карточки,
17,26 →7,70с. Проверены выбор обоих пресетов без автоматической отправки,
блокировка формы во время запроса и компоновка на391/1200 CSS-пикселях без
горизонтального переполнения. Backend и соседние дни не менялись.
