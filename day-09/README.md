# Day 09 — Управление контекстом: сжатие истории

Учебное приложение сравнивает два синхронизированных диалога на одном и том же вопросе:

- **Полный контекст** каждый раз отправляет в LLM всю переписку.
- **Сжатый контекст** оставляет последние `N` сообщений как есть, а более раннюю часть заменяет rolling-summary, созданным той же моделью.

Обе ветки, сообщения, summaries и фактические метрики API хранятся в SQLite. После перезапуска эксперименты остаются доступны.

## Как работает сжатие

Параметры сжатия задаются в «Настройках». Например, при `сжимать каждые 10` и `оставлять последних 6` приложение ждёт 16 несжатых сообщений: 10 для нового фрагмента summary и 6 последних сообщений. Затем агент:

1. отправляет первые 10 сообщений вместе с предыдущим summary в отдельный LLM-вызов и получает структурированную Markdown-сводку;
2. сохраняет новый summary отдельно в SQLite;
3. помечает эти 10 сообщений архивными;
4. в следующем запросе отправляет только system-настройки, summary, последние 6 сообщений и новый вопрос.

Архив остаётся доступен в SQLite для проверки, но не расходует контекст LLM. Если LLM не смогла создать очередной summary, новый фрагмент не архивируется. До первого успешного summary сжатая ветка передаёт всю историю; после прежних успешных сжатий она использует последний сохранённый summary и весь неархивированный хвост. Уже архивированные сообщения не возвращаются в запрос автоматически.

## Запуск одной командой

Нужны Python 3.11+ и Node.js 20+.

```bash
cd day-09
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
npm install
npm --prefix frontend install
cp .env.example .env
# укажите DEEPSEEK_API_KEY или OPENROUTER_API_KEY
npm run dev
```

Откройте [http://127.0.0.1:5175](http://127.0.0.1:5175). Одна команда запускает FastAPI на `5008` и Vue/Vite на `5175`; ключи остаются только на Python-бэкенде.

Проверки:

```bash
npm test
npm run build
```

## Сценарии сравнения для видео

Под полем ввода нажимайте `▦ Шаг`, затем `Сравнить ответы →`. Вопросы только подставляются в поле — отправку вы контролируете сами.

**Реестр лаборатории** содержит девятнадцать насыщенных партиями образцов ходов и финальную сверку восьми ранних и поздних записей. В первом шаге задаётся обращение «Доктор Д», а каждый последующий шаг добавляет дополнительный протокол из 18 записей: код, шкаф, массу, температуру, цвет пломбы и статус. Это проверяет, не потерялись ли точные детали среди большого объёма данных.

Приложение использует `сжимать каждые 10` и `оставлять последние 6`. Каждый шаг сохраняет два сообщения — вопрос и ответ: поэтому summary создаётся после 8-го, 13-го и 18-го шага. Финальная проверка — 20-й шаг. Для summary не задаётся `max_tokens`: он не обрезается искусственным лимитом и может сам выбрать необходимую длину.

Для сравнения:

1. Проведите сценарий до финального контрольного вопроса в новом эксперименте.
2. Сопоставьте два финальных ответа по фактам.
3. Посмотрите «Экономию входа», суммарные токены и стоимость. В сжатом режиме цена summary показывается отдельно и уже включена в итог.
4. Откройте `ⓘ JSON`: в полном режиме будет вся история, в сжатом — summary и последние `N` сообщений.
5. Нажмите «Все summary» в карточке сжатого контекста: откроется вся цепочка созданных сводок, а не только актуальная.

## Что измеряется

После каждого ответа используются только фактические поля `usage`, возвращённые API: входные, выходные и общие токены, время, причина завершения и стоимость при её наличии. Отдельно учитываются успешные сохранённые LLM-вызовы для summary: видно экономию последующих запросов и начальную цену компрессии.

`data/context.sqlite3` и `.env` игнорируются Git — реальная переписка и API-ключи в репозиторий не попадают.

## Порядок вызовов, ошибки и ограничения Day 09

В Day 09 один `POST /api/ask` с `experiment_id`, `prompt`, `controls`, `batch_size` и `keep_recent` последовательно запрашивает полный режим, затем сжатый. Обе ветки получают один новый вопрос и общие настройки, но ответы и дальнейшие истории у них свои. После успешного ответа сжатой ветки агент проверяет порог и при необходимости делает ещё один вызов summary. Новый summary применяется только на следующем ходе; текущий ответ уже сформирован со старым контекстом. За один ход сжимается один batch.

В Day 09 batch_size по умолчанию 10, keep_recent 6; оба параметра — чётные числа от 2 до 100, чтобы не разрезать пары вопрос/ответ. Keep_recent задаёт несжимаемый хвост при создании summary, а не жёсткое окно каждого запроса: между сжатиями несжатая история растёт. При успешных ходах и дефолтах первое сжатие происходит после восьмой пары сообщений. Вызов summary получает предыдущую сводку и очередной фрагмент ранних сообщений, использует ту же модель, temperature 0, thinking disabled, без max_tokens и stop-маркеров. Корректность фактов в Markdown-сводке не проверяется отдельным валидатором.

Исходные настройки ответов Day 09: DeepSeek, `deepseek-v4-flash`, temperature 0, thinking disabled, без max_tokens, формата и stop sequences. Для OpenRouter исходная модель — `openrouter/free`. Ответы допускают max_tokens 1–100000, temperature 0–2 и до 16 stop-маркеров. Поведение summary остаётся отдельным от этих пользовательских настроек.

В Day 09 сбой одного основного ответа не отменяет успех другого: результат каждой ветки возвращается отдельно, история пополняется только там, где ответ успешен. Поэтому после частичного сбоя истории могут различаться по числу ходов. Сбой summary сохраняет уже полученный ответ и возвращается как `summary_error` в API; текущий Vue-интерфейс показывает ошибки основных ответов, но отдельно это поле не выводит. На следующем успешном ходе агент снова проверяет порог сжатия. При позднем сбое сохраняются предыдущая сводка и неархивированные исходные тексты.

«Экономия входа» Day 09 сравнивает prompt_tokens последних сохранённых ответов двух веток. После частичных ошибок это могут быть ответы разных ходов. Итоговые токены включают сохранённые успешные summary-вызовы; неуспешные вызовы не образуют отдельной записи расхода. При отсутствии API cost используется встроенная оценка для известных моделей; неизвестная цена отмечается отдельно. Сжатие может потерять деталь или создать длинную сводку, поэтому уменьшение токенов и качество ответа нужно наблюдать на конкретном эксперименте.
